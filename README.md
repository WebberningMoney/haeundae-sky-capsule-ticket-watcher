# haeundae-sky-capsule-ticket-watcher 🎫

> 在「訂票頁面本身」持續監看指定日期的時段，一有票就用**分頁標題＋紅色面板**提醒你。
> 只監看，**不會下單、不會付款、不會填寫任何個資**。

**English summary** — A single-file browser-console script that polls a maketicket-style booking
page for released slots on chosen dates. It reloads a fresh copy of the page in a hidden
same-origin iframe every round, clicks the target dates, reads the rendered "remaining" text,
and flags any slot that is not sold out. It adapts its polling interval (shorten on success,
back off on failure) to stay under the site's rate limit. It does **not** bypass the site's
anti-bot token and never places orders.

## 它能做什麼／不能做什麼

| ✅ 能做 | ❌ 不做 |
|---|---|
| 定期重新載入並查詢指定日期的各時段剩餘數 | 自動下單、自動付款 |
| 有票時：標題變 `🎫有票! 10/11 5班10:30-11:00`、面板變紅 | 填寫姓名、電話、信箱、密碼等任何個資 |
| 記錄「什麼時間、發現哪天哪個時段、剩幾張」（存在瀏覽器） | 繞過網站的防機器人驗證（`X-Schedule-Token`） |
| 依成功／失敗自動調整查詢頻率，降低被限流的機率 | 在背景常駐（分頁關閉就停止） |
| （選用）瀏覽器桌面通知 | 保證一定搶得到票 |

## 完整流程總覽（前置作業 → 啟動 → 日常 → 異常處理）

整套工具由三個部分組成：

| 部分 | 檔案 | 用途 |
|---|---|---|
| 監控主程式 | [`watcher.js`](./watcher.js) | 在訂票頁裡持續查詢、有票就提醒（**必要**） |
| 自動啟動版（選用） | [`userscript/haeundae-sky-capsule-ticket-watcher.user.js`](./userscript/haeundae-sky-capsule-ticket-watcher.user.js) | 裝進 Tampermonkey 後，每次打開訂票頁就自動啟動，Chrome 重開也不必重貼 |
| 重開 Chrome 小工具（選用） | [`scripts/restart-chrome.command`](./scripts/restart-chrome.command)（macOS）、[`scripts/restart-chrome.bat`](./scripts/restart-chrome.bat)（Windows，未實測） | 你**手動**執行時，正常關閉所有 Chrome 視窗並重新打開訂票頁 |

**兩種啟動方式，選一個就好：**
- **方式 A｜貼到 Console**：不用安裝任何東西，3 分鐘搞定；缺點是 Chrome 重開後要重貼。→ [快速開始](#快速開始給完全沒有程式基礎的人)
- **方式 B｜Tampermonkey 自動啟動**：一次性設定（約 5 分鐘），之後打開訂票頁就自動跑。→ [自動啟動](#自動啟動tampermonkeychrome-重開後自動接續)

**整體流程：**

| 階段 | 你要做什麼 | 詳細說明 |
|---|---|---|
| 0. 前置作業 | 用電腦版 Chrome；電腦接電源、網路穩定；系統允許 Chrome 通知（macOS 關掉「專注模式」）；（方式 B）安裝 Tampermonkey 並開啟「允許使用者指令碼」 | [檢查表](#開始前的檢查表請逐項打勾)、[提醒設定](#提醒設定桌面版-chromemacoswindows)、[Tampermonkey](#自動啟動tampermonkeychrome-重開後自動接續) |
| 1. 啟動 | 打開訂票頁 →（方式 A）貼上 `watcher.js`；（方式 B）什麼都不用做 | [快速開始](#快速開始給完全沒有程式基礎的人) |
| 2. 啟動後確認 | 右上角出現黑色面板；**在頁面上點一下**（Chrome 規定要點過才能出聲）；可用 `__ticketWatcher.testAlert()` 測試提醒 | [畫面說明](#畫面說明) |
| 3. 日常 | 分頁放前景（或獨立視窗）、電腦不睡眠；**有票就立刻到網站下單**（工具不代勞） | [End-user 注意事項](#end-user-注意事項) |
| 4. 被限流 | 面板出現「被網站限流(429)，暫停到 HH:MM」→ **什麼都不用做**，程式會自動暫停約 26 分鐘後試探並恢復 | [自適應間隔與限流](#自適應間隔與限流) |
| 5. Chrome 重開／當機 | 方式 B：自動接續；方式 A：重貼一次。需要手動重開時可用[重開 Chrome 小工具](#重開-chrome-小工具手動執行) | 同上 |
| 6. 停止／收尾 | Console 輸入 `__ticketWatcher.stop()` 或關掉分頁；Tampermonkey 用戶把腳本關閉；要留紀錄先 `__ticketWatcher.exportHistory()` | [除錯與內部狀態](#除錯與內部狀態) |
| 7. 更新程式 | 方式 A：重新複製 `watcher.js`；方式 B：重新安裝最新的 `.user.js`（**不會自動更新**，避免程式被悄悄換掉） | [Tampermonkey](#自動啟動tampermonkeychrome-重開後自動接續) |

## 快速開始（給完全沒有程式基礎的人）

> 全程只需要「複製、貼上、改兩個數字」，**不需要安裝任何東西**。大約 3 分鐘。

### 開始前的檢查表（請逐項打勾）

| ✔ | 項目 | 說明／怎麼做 |
|---|---|---|
| ☐ | 用**電腦版**瀏覽器 | 建議 Chrome。手機瀏覽器無法使用（沒有 Console）。 |
| ☐ | 電腦**接上電源**、網路穩定 | 監控要跑很久，沒電或斷網就會停。 |
| ☐ | 已打開**訂票頁**，並且看得到「預訂日期」日曆 | 網址通常長這樣：`https://…/ticket_chn/GDxxxxxxx`。**不是首頁、不是「我的訂單」頁**。 |
| ☐ | 這個分頁要**放在前景**（可以自己開一個獨立視窗） | 分頁被切到背景太久，瀏覽器會讓它變很慢，甚至停住。 |
| ☐ | 準備好要監看的**月份**和**日期** | 例如「10 月的 10 到 13 號」。 |
| ☐ | **不要**同時開多個監控 | 同一個分頁重複貼上會自動取代舊的，但多個分頁/多台電腦一起跑會讓網站更容易限流。 |

### 步驟

**步驟 1｜打開 Console（開發人員工具）**

| 系統 | 快捷鍵 |
|---|---|
| Mac | `⌥` + `⌘` + `J`（Option + Command + J） |
| Windows | `F12`，再點上方的 **Console** 分頁 |

> 會看到一個可以打字的區域，這就是 Console。**看到黃色警告或紅色字不用怕**，那是網站自己的訊息。

**步驟 2｜複製程式**
打開 [`watcher.js`](./watcher.js)，全選（`⌘A`／`Ctrl+A`）→ 複製（`⌘C`／`Ctrl+C`）。

**步驟 3｜改兩個地方（其他都不用動）**
先把程式貼到任何純文字編輯器（記事本、備忘錄、GitHub 網頁的編輯器都可以），找到最上方這一段：

```js
month: 10,        // ← ① 你要監看幾月（1~12）
...
days: '10-13',    // ← ② 你要監看幾號
```

- 只改**數字**，**不要刪掉**逗號 `,`、引號 `' '`、冒號 `:`。
- `days` 的寫法：`'10-13'`（10 到 13 號）、`'10,12,15-17'`（10、12、15~17 號）、`'25'`（只有 25 號）。
- **月份不用自己算按幾次 Next**，程式會自動看日曆現在是幾月，再自己切過去。

**步驟 4｜貼到 Console 並按 Enter**
回到瀏覽器 Console，貼上（`⌘V`／`Ctrl+V`），按 `Enter`。

> 🔒 **Chrome 的防貼上保護**：第一次貼可能出現提示，要你先輸入 `allow pasting` 並按 Enter，然後再貼一次。這是瀏覽器的安全機制，正常現象。

**步驟 5｜確認有啟動**
畫面右上角出現**黑色大字面板**，就代表成功了。之後：

- 面板**變紅**、分頁標題出現 `🎫有票!` → 有票了，**請立刻到網站下單**。
- 如果面板一開始就顯示 **⚠️ 無法啟動**，照上面的中文提示處理即可（例如「日期寫反了」、「這個頁面找不到日曆」）。點一下面板可以關掉它。

**停止**：在 Console 輸入 `window.__ticketWatcher.stop()` 按 Enter；或直接關掉這個分頁。

### 程式已經幫你自動處理的事

| 以前要手動做 | 現在 |
|---|---|
| 算「要按幾次 Next」才到目標月份 | ✅ 自動讀取日曆、自動按 Next／Prev |
| 日期要寫成 `[10,11,12,13]` 陣列 | ✅ 直接寫 `'10-13'`，全形數字、空格、`、` 都能容忍 |
| 手動重新整理頁面看最新狀態 | ✅ 在隱藏頁面自動重載，且每次點日期都會向伺服器查詢最新資料 |
| 一直盯著螢幕等票 | ✅ 有票時：系統通知＋提示音＋溫柔女聲＋標題閃爍＋紅點＋面板變紅 |
| 被網站限流後不知所措 | ✅ 自動暫停約 25 分鐘（實測封鎖約 26～29 分鐘會自己解除），之後每 2 分鐘只送 1 個試探請求；發桌面警示並記錄診斷資訊。**不需要重開 Chrome** |
| 不知道自己送了多少查詢 | ✅ 面板顯示查詢預算 `已用/上限`，並自動節流 |
| 網站彈出「요청실패」視窗卡住 | ✅ 自動攔截，改為記錄並退避 |
| 電腦閒置自動睡眠 | ✅ 自動要求「保持螢幕喚醒」（仍建議接電源） |
| Chrome 重啟後從頭摸索頻率 | ✅ 自動存檔、自動接續、必要時先冷卻 |
| 貼錯頁面、日期寫錯不知道哪裡錯 | ✅ 啟動前自動檢查，並用中文告訴你怎麼改 |
| 通知權限 | ✅ 若開啟 `desktopNotification`，啟動時自動請求一次 |

### 程式**無法**自動處理、需要你自己做的事

1. **打開正確的訂票頁**（程式不能替你決定要監看哪個商品）。
2. **貼上程式並按 Enter**（瀏覽器規定一定要由人操作）。第一次貼可能要先輸入 `allow pasting`。
3. **保持這個分頁在前景、電腦有電有網。** 瀏覽器不允許網頁程式阻止「整台電腦關機／合上螢幕睡眠」。
4. **Chrome 完全關閉重開後，需要重新貼一次**（或改用下一節的 Tampermonkey 自動啟動）。
5. **有票後，你要自己下單付款**，工具不會代勞。

## 自動啟動：Tampermonkey（Chrome 重開後自動接續）

> 適合：要長時間掛著、Chrome 可能重開或當機的人。設定一次，之後**打開訂票頁就自動開始監控**，不必再貼程式。
> ⚠ 這一節的流程**還沒有在作者的電腦上實測過**（程式檔本身有測試，但「Tampermonkey 安裝與自動執行」沒有）；
> 如果某一步和你看到的畫面不同，請退回[方式 A（貼到 Console）](#快速開始給完全沒有程式基礎的人)，並歡迎回報。

**前置作業（各做一次）**
1. 到 Chrome 線上應用程式商店安裝 **Tampermonkey**（或 Violentmonkey）。
2. 打開 `chrome://extensions` → 找到 Tampermonkey → 按「**詳細資料**」→ 打開「**允許使用者指令碼**」開關。
   新版 Chrome（約 138 版起）沒開這個，使用者腳本**完全不會執行**，這是最常見的失敗原因。若你的版本沒有這個開關，改開右上角「開發人員模式」。

**安裝腳本**
3. 點這個連結：
   [`haeundae-sky-capsule-ticket-watcher.user.js`](https://raw.githubusercontent.com/WebberningMoney/haeundae-sky-capsule-ticket-watcher/main/userscript/haeundae-sky-capsule-ticket-watcher.user.js)
   → Tampermonkey 會開一個安裝頁 → 按「**安裝**」。
   （如果沒有跳出安裝頁：Tampermonkey 圖示 →「新增腳本」→ 全選刪掉預設內容 → 貼上該檔全文 → `⌘S`／`Ctrl+S`。）
4. **確認要監看的月份與日期**：Tampermonkey 圖示 →「管理面板」→ 點該腳本 → 編輯器裡找到 `month: 10`、`days: '10-13'`，
   只改數字，存檔（`⌘S`／`Ctrl+S`）。其他設定（例如查詢速度）也是在同一個地方改，見[設定參數](#設定參數)。
   **想改查詢速度，要同時改兩個地方**：`rotate.everyMs`（每隔多久查 1 天）和 `budget.maxCalls`（30 分鐘最多查幾個，是安全上限）。
   只改 `everyMs` 沒有用，實際速度會被預算壓回去（面板會說明）。對照：

   | 想要 | `rotate.everyMs` | `budget.maxCalls` |
   |---|---|---|
   | 每 30 秒查 1 天（預設，每分鐘 2 個） | `30_000` | `60` |
   | 每 20 秒查 1 天（每分鐘 3 個） | `20_000` | `100` |
   | 每 10 秒查 1 天（每分鐘 6 個，實測約半小時就被擋一次） | `10_000` | `200` |

5. 如果你監看的是**別的商品**：同一個編輯器最上面的 `// @match` 那行，把網址改成該商品的訂票頁（結尾保留 `*`）。

**驗證**
6. 打開（或重新整理）訂票頁。幾秒內右上角應該出現黑色面板。**在頁面上點一下**，提示音與語音才會啟用。
7. 沒有面板？依序檢查：①「允許使用者指令碼」有沒有開 ② Tampermonkey 圖示上該腳本是否為開啟 ③ `@match` 網址是否和你的分頁網址相符
   ④ Console 有沒有紅字錯誤。

> **用 AdGuard 也可以**：AdGuard 瀏覽器擴充功能內建使用者腳本功能。點上面的連結時，如果是 AdGuard 攔下來安裝，也一樣能用
> （實測：能安裝、能啟動）。更新版本時，到 AdGuard 的使用者腳本管理頁刪掉舊的再裝新的即可。
> **2.1.0 以前的版本有個問題**：腳本比網頁早執行時，會因為日曆還沒出現而直接顯示「無法啟動：找不到日曆」，2.1.1 起改成會先等（最多 30 秒）。

**日常**
- Chrome 重開後，**只要再打開訂票頁**（或用[重開 Chrome 小工具](#重開-chrome-小工具手動執行)一次做完），監控就自動啟動。
- 暫停：Tampermonkey 圖示 → 把該腳本切成關閉；或 Console 輸入 `__ticketWatcher.stop()`。
- **不會自動更新**（標頭設為 `@updateURL none`／`@downloadURL none`）。原因：避免程式被悄悄換掉、也避免你改好的設定被覆蓋。
  要更新就重新做第 3 步，再把第 4 步的設定改回來。
- 這份使用者腳本是由 `watcher.js` **自動產生**的（`npm run build:userscript`），內容一模一樣，只是標頭不同：
  只在這個商品頁啟動、不在腳本自己建立的隱藏 iframe 裡啟動（`@noframes`）、不自動更新。

> 也可以不裝 Tampermonkey，直接把整份 `watcher.js` 存成使用者腳本；差別只是 `@match` 預設涵蓋所有 `https://*/ticket_chn/*` 頁面，範圍比較大。

## 重開 Chrome 小工具（手動執行）

`scripts/` 底下有一支小工具：**正常關閉所有 Chrome 視窗 → 等 Chrome 完全結束 → 重新打開訂票頁**。

| 系統 | 檔案 | 狀態 |
|---|---|---|
| macOS | [`scripts/restart-chrome.command`](./scripts/restart-chrome.command) | 語法與內容有自動測試；**「關閉 → 重開」的完整流程沒有在測試中真的執行過**（會關掉正在跑的監控） |
| Windows | [`scripts/restart-chrome.bat`](./scripts/restart-chrome.bat) | **未在 Windows 實測** |

**怎麼用（macOS）**

在「終端機」進到專案資料夾後執行（把網址換成你的訂票頁；不給網址就用檔案裡的預設）：

```bash
bash scripts/restart-chrome.command
```

- 不想開終端機：在 Finder 雙擊 `restart-chrome.command`。**但只有用 `git clone` 取得的檔案才保有「可執行」權限。**
  如果你是在 GitHub 網頁上單獨下載這個檔案、或下載 ZIP，權限會遺失，雙擊時會跳出：
  `The file "restart-chrome.command" could not be executed because you do not have appropriate access privileges.`
  解法：在終端機對該檔案執行一次 `chmod +x`（例如 `chmod +x ~/Downloads/restart-chrome.command`），之後就能雙擊；
  或一律用上面的 `bash …` 指令執行，就不受權限影響。
  （若跳出「無法打開，因為無法驗證開發者」，改用「右鍵 → 打開」。）
- 第一次執行時 macOS 會問「終端機想要控制 Google Chrome」，按「好」。
- Windows：雙擊 `scripts\restart-chrome.bat`，或在命令提示字元執行。

**重開後怎麼恢復監控**
- 用了 Tampermonkey（方式 B）：什麼都不用做，訂票頁一開就自動啟動。
- 沒用 Tampermonkey（方式 A）：等訂票頁載入後，重新貼一次 `watcher.js`（[快速開始](#快速開始給完全沒有程式基礎的人)的步驟 1～4）。

**使用前請務必知道**
1. **只有你手動執行時才會動。** 監控程式不會、也不能呼叫它；本專案**刻意沒有**「被限流就自動重開／自動換身分」這種機制（測試會檢查 `watcher.js` 不含這類呼叫）。
2. **會關掉所有 Chrome 視窗與分頁**，其他工作請先存好。
3. **歷史紀錄可能消失**：若你的 Chrome 設定為「關閉時清除網站資料」（作者的環境實測是這樣），監控的歷史與存檔會一起被清掉。
   重開前先在訂票頁的 Console 執行 `__ticketWatcher.exportHistory()` 下載 CSV。
4. **它不是「解除限流」的按鈕，也不建議拿來繞過限流。** 被限流時，封鎖約 26～29 分鐘會自己解除，程式會自動等待並恢復。
   重開 Chrome 在某些環境下可能讓網站當成新的瀏覽階段而提早恢復，但這**不保證有效**，而且如果重開後繼續用會被擋的速度查詢，
   只會再被擋，甚至可能升級成更長、更大範圍的封鎖，連你自己手動訂票都受影響。重開後請維持原本保守的查詢速度。
5. 這個工具適合的情境：Chrome 卡住、記憶體過高、擴充功能異常、想要一個乾淨的瀏覽器環境。

## 設定參數

全部在 `watcher.js` 最上方的 `CONFIG`。**一般人只要改 `month` 和 `days` 兩個。**

| 參數 | 預設 | 說明 |
|---|---|---|
| `month` | `10` | **要監看幾月**（1~12）。程式會自動切換到該月，不用自己算按幾次 Next。 |
| `year` | `null` | 年份。`null` = 自動（沿用頁面顯示的年份；目標月份比目前顯示的早，就當作明年）。 |
| `days` | `'10-13'` | **要監看哪幾號**。可寫 `'10-13'`、`'10,12,15-17'`、`'25'` 或 `[10,11]`。建議一次不超過 7 天。 |
| `interval.start` | `60000` | 起始「每輪結束後的休息時間」（毫秒）。 |
| `interval.step` | `10000` | 每次成功縮短／失敗退回的幅度。 |
| `interval.floor` | `30000` | 休息時間下限（毫秒）。**越小越容易被限流**（舊預設 10000 約 20～30 分鐘就被擋）。⚠ 預設開著 `budget.pace` 時，實際每輪間隔由預算節流決定（4 天 ÷ 預算 60 ＝ 每 120 秒一輪），這個值通常**不是**實際間隔。 |
| `interval.max` | `180000` | 失敗退避時的上限。 |
| `interval.probeAfterOk` | `10` | 因失敗被鎖住的下限，需在該下限連續成功幾次才放寬一級。 |
| `initialDelay` | `0` | 啟動後先等多久再開始第一輪。剛被限流時可設 `240000`（4 分鐘）。 |
| `reloadEvery` | `120` | 每幾輪才整頁重新載入一次（預設約 4 小時）。設 `1` = 每輪都重載（請求量約多一倍，較容易被限流）。一次重載約 61 個請求；2026-09-29 有一次被擋剛好發生在重載後的第一個查詢，所以預設放得很寬。頁面出問題時仍會立刻重載。輪流模式下以「輪」計（每個日期各查一次算一輪）。 |
| `blockedWaitMs` | `1500000` | 第一次被限流（429）後先暫停多久再送第一個試探（25 分鐘；依實測封鎖約 26～29 分鐘）。見「限流」一節。 |
| `blockedRetryMs` | `120000` | 第一個試探仍被擋時，之後每隔多久再試 1 個請求（2 分鐘）。 |
| `budget.windowMs` / `budget.maxCalls` | `30 分鐘` / `60` | 查詢預算：視窗內最多送幾個時段查詢（約每分鐘 2 個）。`maxCalls: null` = 不限制（不建議）。被擋時會自動調降。實測 90 個/30 分鐘也被擋過，見「限流」一節。 |
| `budget.learnFactor` / `budget.min` | `0.7` / `30` | 被擋時，新預算 = 窗口內查詢量 × 0.7（不低於 30）。 |
| `rotate.enabled` / `rotate.everyMs` / `rotate.jitterMs` | `true` / `30000` / `2000` | **輪流模式（溫和模式）**：每次只查 1 天、日期輪流查，而不是每輪連查全部日期。每隔 `everyMs` 查 1 天（預設 30 秒 ＝ 每分鐘 2 個），`jitterMs` 是隨機抖動（±）。實際間隔取 `everyMs` 與預算平均分散較大者。開啟時 `interval.*` 只在失敗退避時使用；`enabled: false` 回到每輪連查全部日期。**越快越容易被限流**（每 10 秒 1 個 ＝ 每分鐘 6 個，約等於曾被擋的速率）。 |
| `budget.pace` | `true` | 預算「平均分散」：兩輪**開始**之間至少相隔 `視窗 × 每輪查詢數 ÷ 預算`（預設 30 分鐘 × 4 ÷ 60 ＝ 120 秒）。它比自適應休息長時，以它為準。設 `false` 則只受休息時間與預算上限控制（會先猛送、再被預算擋到長時間停擺，較容易被限流）。 |
| `timing.startupWaitMs` | `30000` | 腳本啟動時，最多等多久讓日曆出現。用 Tampermonkey／AdGuard 這類使用者腳本時，腳本常比網頁自己畫日曆的程式更早執行，所以要耐心等；逾時才判定「不是訂票頁」。網路很慢可調大。 |
| `timing.readyTimeoutMs` | `20000` | 等頁面載入並出現日曆的上限。網路慢就調大。 |
| `timing.ajaxTimeoutMs` | `12000` | 點日期後，等該次查詢回應的上限。 |
| `timing.jitter` | `400~1200` | 每天之間的隨機間隔，避免規律到像機器。 |
| `notify.*` | 全開 | 提醒方式，見下方「提醒設定」。 |
| `panel.fontPx` / `panel.widthPx` | `40` / `820` | 面板字體大小與寬度。 |
| `resume.*` | 開 | 中斷後自動接續（見下節）。 |
| `keepAwake` | `true` | 自動要求瀏覽器保持螢幕喚醒（不能阻止電腦關機／合蓋睡眠）。 |
| `workerTimers` | `true` | 用 Web Worker 計時，降低分頁在背景被 Chrome 節流的影響；失敗會自動退回一般計時。 |
| `allowMultipleTabs` | `false` | 是否允許多個分頁同時監控（不建議）。 |
| `maxHistory` | `200` | 歷史紀錄存檔（`localStorage`）最多保留幾筆；面板只顯示最近 6 筆；記憶體中超過兩倍（400 筆）會修剪回這個數字。完全關閉 Chrome 後網站資料可能被清掉（作者環境實測會），要長期留存請用 `__ticketWatcher.exportHistory()` 匯出 CSV。 |

**不想改檔案？** 貼程式「之前」先在 Console 執行下面這行，就能覆寫任何設定。例如改成每 10 秒查 1 天
（每天約 40 秒查一次；**越快越容易被限流**，被擋時程式會自動暫停並把預算調降）：

```js
window.ticketWatcherConfig = { rotate: { everyMs: 10000 }, budget: { maxCalls: 200 }, reloadEvery: 360 };
```

`budget.maxCalls` 也要跟著調高（30 分鐘 200 個 ≈ 每 9 秒 1 個），否則預算會把速度壓回每 30 秒 1 個；
`reloadEvery: 360` 是為了讓重載維持在約 4 小時一次（360 輪 × 4 天 × 10 秒）。

## 運作原理（詳細）

### 整體流程

```
  ┌───────────────────────── 每一輪 ─────────────────────────┐
  │ 1. 需要時才建立隱藏 iframe → 載入全新訂票頁               │
  │    （預設每 120 輪，或失敗後）                            │
  │ 2. 用 jQuery.active 等頁面「閒置」，再自動切到目標月份     │
  │ 3. 逐日：點日期 → 旁聽網站自己發的時段查詢                 │
  │      ・以請求裡的 sdDate 確認是「這一次點擊」的回應         │
  │      ・直接拿 HTTP 狀態碼 + JSON（sdName／sdRemainder）    │
  │ 4. sdRemainder > 0 即有票；與上一輪比對，只提醒「新出現」  │
  │ 5. 依結果調整休息時間 → 休息 → 下一輪                     │
  └────────────────────────────────────────────────────────────┘
```

### 事件驅動（v2 的核心改進）

舊版靠「固定等 3 秒再讀畫面」，慢又不可靠：慢的請求可能讀到上一天的舊資料，
而「讀不到文字」也分不出是被限流還是別的原因。v2 改成：

- **等到才往下走**：頁面閒置、月份真的換了、這次點擊的回應真的回來，才繼續。
  一輪從約 23 秒縮短到約 4～6 秒，偵測延遲大幅降低。
- **確認資料屬於被點的那一天**：比對請求裡的 `sdDate`；收到別天的資料會判為 `stale` 並重試。
- **精準的錯誤分類**：直接讀 HTTP 狀態碼，見下表。
- **JSON 為主、畫面為輔**：讀得到 JSON 就用 JSON（已實測與畫面文字逐筆一致）；
  API 格式改變時自動退回讀畫面文字。

### 錯誤分類

| 種類 | 觸發 | 處理 |
|---|---|---|
| `rate_limit` | HTTP 429 | **硬失敗**：退回上一級並鎖定下限；先暫停 `blockedWaitMs`（預設 25 分鐘），之後每 `blockedRetryMs`（2 分鐘）只送 1 個請求試探；有 `Retry-After` 就照做；發桌面警示 |
| `blocked` | HTTP 403 | 同上 |
| `server` | HTTP 5xx | 同上 |
| `load` | 頁面載入逾時／日曆沒出現 | 同上（多半是被暫時擋住） |
| `timeout` `stale` `network` | 等不到回應／收到別天資料／網路錯誤 | **軟失敗**：間隔不變，下一輪重新載入頁面再試 |
| `notopen` | 切不到目標月份 | 該月份可能尚未開放，面板顯示提示並持續等待（不會停止） |
| `layout` | 找不到日曆／按鈕 | 連續 3 次就停止並提示「網站可能改版」 |
| （非失敗）該日無場次 | 200 且資料為空 | 記為「無場次」，不算錯誤 |

### 為什麼不直接呼叫 API？

網站發時段查詢前，頁面會先跑一段**工作量證明（proof-of-work）**：
`/ticket/challenge` → 計算 → `/ticket/issueToken`，取得一個**有效 10 分鐘**的 token，
放在 `X-Schedule-Token` 標頭。這是防機器人機制，直接呼叫會被 403。
本專案**刻意不偽造它**：仍由頁面自己發請求，我們只在 `ajaxComplete` 事件「旁聽」結果，
並且主動降頻。請勿修改成繞過防護的版本。

### 為什麼預設不再每輪重載頁面？

每次載入頁面，都會多出：頁面本身、`challenge`、`issueToken`、月份清單等請求（實測約 5 個），
而且要重算一次工作量證明。網站的 token 有效 10 分鐘，過期時頁面會自己換新的，
所以**沿用同一頁一樣拿得到最新資料**（每次點日期都會向伺服器查詢）。
實測第 2 輪起每輪只有 4 個請求（每天 1 個）。

### 輪流模式（溫和模式，預設）

舊做法是每輪「連續」查全部日期（例如 4 天 = 一次連送 4 個請求，再休息一兩分鐘），這對伺服器來說是一個小突發。
輪流模式改成**每次只查 1 天**，日期輪流查：

- 平均請求量不變（預設每 30 秒 1 個 = 每分鐘 2 個），但不再有「一次連送 N 個」的突發。
- 每一天被檢查的頻率 = `rotate.everyMs` × 天數（4 天、30 秒 → 每天約 2 分鐘查一次）。
- 各天最近一次的結果會合併成完整快照，所以提醒、標題、面板、歷史紀錄都跟原本一樣；
  同一張票不會因為輪到別天而「消失又重複提醒」；某天連續查不到結果超過 5 分鐘，就不再採信它的舊結果。
- 實際間隔 = `max(rotate.everyMs, 預算平均分散)`。被 429 擋到後，預算會自動調降，間隔就自動拉長。
- 這是「更均勻」不是「更安全」：它能不能少被擋，仍要靠實測；請看「限流」一節的紀錄。

### 有票怎麼判斷？

API 每個時段回傳 `sdName`（如 `20회차(18:00 ~ 18:30) 입장`）與 `sdRemainder`（剩餘數）。
`sdRemainder > 0` 就是有票。備援模式下則讀畫面文字 `[剩余:N]`，「售罄」不含數字所以不會匹配。

### 為什麼要攔截 `alert`？

請求失敗時網站會 `alert('요청실패')`。alert 會**阻塞整個分頁**，導致自動化卡死。
腳本在 iframe 載入期間持續把 `alert` 換成「只記錄、不彈窗」的函式（記錄最多保留 50 筆）。

### 如何避免「新票重複通知」？

用 `日期|時段名稱` 當 key，保存上一輪有票的 key 集合，**這一輪有、上一輪沒有**的才算新增。
這份集合也會存進接續存檔：Chrome 中斷不久就重啟，不會重複通知；中斷很久，仍存在的票會重新提醒一次。

### 如何避免多個迴圈／多個分頁同時跑？

- 同一分頁：每次啟動產生唯一 `RUN_ID`，舊迴圈每一步都檢查，發現不是自己就退出。
- 多個分頁：用 `localStorage` 心跳（每 10 秒，Worker 計時）偵測；超過 90 秒沒有心跳就視為對方已不在。
  另一個分頁真的在監控時，新的會拒絕啟動並用中文說明。重新整理或關閉分頁時會主動釋放鎖（`pagehide`），
  所以重新整理後可以立刻重新啟動；只有瀏覽器當機這類意外情況才需要等最多 90 秒。

### 計時器與背景分頁

優先使用 **Web Worker 計時**：Chrome 對背景分頁會把主執行緒的計時器降到每分鐘一次，
Worker 不受同樣限制。若網站的安全設定不允許 Worker，會自動退回一般計時（啟動記錄會註明）。
> 注意：這只保證「程式的排程」不被拖慢；分頁完全被隱藏時，瀏覽器仍可能降低頁面本身的效能，
> 所以仍建議把此分頁放在前景或獨立視窗。

## 中斷後自動接續（Chrome 重啟／分頁重開）

監控程式活在分頁的記憶體裡，**Chrome 重啟、分頁被關掉或重新整理，程式就會消失**。
為了不必每次都從頭摸索，程式會在**每一輪結束後**把以下資訊存進 `localStorage`
（鍵名 `__ticket_watcher_state`）：

- 目前學到的休息間隔、生效的下限、退回用的間隔堆疊
- 已完成輪數、在下限連續成功的次數
- 上次是否以失敗收尾、存檔時間

重新啟動時：

| 情況 | 行為 |
|---|---|
| 沒有存檔，或存檔超過 24 小時 | 從 `interval.start` 重新開始 |
| 有存檔，且中斷時間短（< 10 分鐘）且上次成功 | 直接沿用學到的間隔繼續 |
| 有存檔，但中斷過久（> 10 分鐘）**或**上次以失敗收尾 | 沿用間隔，但**先冷卻 2 分鐘**再開始，避免一啟動就撞上尚未解除的限流 |

想清掉存檔重新開始：`window.__ticketWatcher.resetSaved()`，再重新貼上腳本。

**想讓它在分頁一開就自動啟動？** 請看[自動啟動：Tampermonkey](#自動啟動tampermonkeychrome-重開後自動接續)
（專案已附好可直接安裝的使用者腳本）。
> 程式開頭已內建 `if (window.top !== window.self) return;`，只會在最上層視窗執行，
> 不會在腳本自己建立的隱藏 iframe 裡重複啟動（否則會遞迴失控）。

## 自適應間隔與限流

> **預設的輪流模式（`rotate.enabled: true`）不使用「休息時間」**：成功時固定每 `rotate.everyMs` 查 1 天；
> `interval.*` 只在失敗退避時才用。下面這一段講的是 `rotate.enabled: false`（每輪連查全部日期）時的行為。

「休息時間」= 一輪**結束後**到下一輪**開始前**的等待（自適應：成功就縮短、失敗就退回）。一輪本身約 4～6 秒。

**實際的輪與輪之間隔 = max（一輪耗時＋休息時間，預算節流的最小間隔）**。預設開著預算節流（`budget.pace`），
最小間隔 = 視窗 30 分鐘 × 每輪 4 個查詢 ÷ 預算 60 ＝ **120 秒**。所以預設情況下，休息時間即使縮到下限 30 秒，
實際仍是「每 120 秒開始一輪」（面板的「下一輪」倒數大約從 115 秒開始，因為掃描本身要花幾秒）。
休息時間的自適應，只有在節流間隔比它短時才會生效（例如把 `budget.maxCalls` 調高，或設 `budget.pace: false`）。

| 事件 | 行為 |
|---|---|
| 一輪成功 | 休息時間縮短一級（`step`），直到下限 |
| 硬失敗（429／403／5xx／載入失敗） | 退回**上一個用過的休息時間**並把它設為新下限；並暫停後只送 1 個請求試探（見上表） |
| 軟失敗（逾時／舊資料／網路） | 間隔不變，下一輪重新載入頁面再試 |
| 連續失敗 | 等待時間再乘倍數（最多 5 倍）；伺服器有給 `Retry-After` 就以較長者為準 |
| 在下限連續成功 10 次 | 才把「因失敗而抬高的下限」放寬一級，小心重新試探 |
| 限流解除 | 記錄「這波限流持續了幾分鐘」（`state.blocks`），並在記錄裡註明 |

### 限流：已知的事實、我們的推論、還不知道的事

網站對「時段查詢」（`getDateScheduleList`）有限流，超過會回 **HTTP 429**，內容是
`{"error":"TOO_MANY_REQUESTS"}`。以下把**觀察到的事實**和**推論**分開寫。

**已確認的事實**

| 事實 | 依據 |
|---|---|
| 被擋的只有「時段查詢」，同一時間月份清單等其他請求仍是 200 | 實際擷取到回應 |
| 被擋時就算剛換了全新的 token（`challenge`→`issueToken` 都成功），時段查詢仍是 429 | 同上 |
| 載入一次頁面 = **約 61 個請求**（約 50 個靜態檔案＋第三方腳本＋4 個 XHR）；一輪查詢只有 4 個 | 讀取 iframe 的 `performance` 紀錄 |
| 頁面沒有偷偷多發時段查詢：每 83 秒的 XHR 剛好 = 1 個 challenge + 1 個 issueToken + 1 個月份清單 + 每輪 4 天 | 同上 |
| 較早的幾次被擋，都在連續輪詢約 20～30 分鐘、送出數百個請求之後；最近一次（17:41）則是在連續 126 分鐘、窗口內只有 87 個查詢時，見下方「後續觀察」 | 執行記錄（估計值） |
| 前 4 次事件的恢復，都發生在「使用者重開 Chrome」之後。**但後來 14:51 有一次沒重開就自己恢復了**（見下方實驗紀錄），所以「只有重開才會好」不成立 | 事件時間軸＋下方實驗 |
| 重開 Chrome 後，網站的 `localStorage`（存檔）會是空的 | 連續 3 次重開都觀察到 |
| 頁面上 JavaScript 看得到的 Cookie 只有一個 `SCOUTER`（效能監控用），看不到 session／登入 Cookie | `document.cookie`（`HttpOnly` Cookie 本來就看不到，所以**不能因此斷定沒有**） |
| 部分使用者的電腦裝有廣告／內容過濾軟體（頁面資源紀錄中可見被注入的本機腳本），瀏覽器流量會先經過它；這可能影響連線與請求行為，是排查時需要留意的環境因素 | 頁面資源紀錄 |

**曾經寫錯、現在更正的說法**

> 舊版 README 曾寫「限流約 6～9 分鐘自動解除，所以重開 Chrome 不是功勞」。**這個結論不成立。**
> 當初只是發現「恢復時間都落在 6～9.5 分鐘」，但那些恢復時間本來就是「使用者重開 Chrome 的時間」，
> 並不是「自己解除的時間」，沒有任何一次是不重開就恢復的。所以只能說：**目前分不出是「時間到了自己解除」還是「重開 Chrome 讓伺服器認不得你」**。

**實驗紀錄（2026-09-29）：封鎖大約持續 26～29 分鐘，會自己解除**

| 時間 | 距第一次 429 | 視窗／動作 | 結果 |
|---|---|---|---|
| 14:21:36 | 0 | 一般視窗（監控中，本次已送 129 個查詢） | 429 |
| 約 14:22–14:24 | 約 1～3 分 | **無痕視窗**（使用者手動點一次） | 正常 |
| 14:25:00 | 3.4 分 | 一般視窗（對照，1 個請求） | 429 |
| 14:37:53 | 16.3 分 | 一般視窗（新載入頁面、新 token、1 個請求） | 429 |
| 14:43:55 | 22.3 分 | 一般視窗的**全新分頁**（1 個請求） | 429 |
| 14:46:54 | 25.3 分 | 自動試探（1 個請求） | 429 |
| **14:51:02** | **29.4 分** | 同一個分頁、**沒有重開瀏覽器** | **正常** |

- **封鎖是暫時的**：25.3 分鐘仍被擋、29.4 分鐘已恢復，沒有做任何處置。中間送了 5 次被擋的試探／對照請求，
  也沒有延長封鎖（最後一次被擋後過 4 分鐘就解除）。
- **新載入頁面、換新 token、開新分頁都沒有用**，只是時間到了才解除。
- 被擋的**當下**，無痕視窗是正常的 → 封鎖綁在某種「用戶端身分」，不是全站或整個 IP。
  但當時無痕視窗同時也「沒有 Cookie」、「沒有被自動化工具控制」，這兩個因素還沒有拆開。
- 伺服器的 429 只有 `{"error":"TOO_MANY_REQUESTS"}`，**沒有 `Retry-After`、沒有任何限流標頭**。
- 網站的取 token 腳本不碰 Cookie／`localStorage`／`sessionStorage`／`IndexedDB`，也沒有瀏覽器指紋；
  前端 JS 沒有偵測自動化的關鍵字，`navigator.webdriver` 為 `false`。所以身分是**伺服器端**用瀏覽器自動帶上的東西認的（JS 看不到）。

**曾寫錯又更正的兩個結論**
1. 「限流約 6～9 分鐘自動解除」：當時的「恢復時間」其實是使用者重開 Chrome 的時間。
2. 「至少 16～22 分鐘不會自己解除，重開才有用」：只是當時還沒等到，實際約 26～29 分鐘就會解除。
   **重開 Chrome 或換無痕視窗只是「更早換成新的身分」的捷徑，不是必要的。**

**後續觀察（同一天稍晚）**：改成「查詢預算 30 分鐘 90 個、每輪平均分散」之後，連續執行 **61 分鐘、共 176 個時段查詢（平均每分鐘 2.9 個，任何 30 分鐘窗口內最多約 88～90 個）沒有被擋**。
對照被擋那次：30 分鐘窗口內累積 129 個（18 分鐘內送出，約每分鐘 7 個）。

**但「90 個以內是安全的」很快就被推翻了**（17:41:26，同一個身分、沒有重開瀏覽器）：

| 項目 | 數字 |
|---|---|
| 已連續執行 | 126 分鐘、365 個時段查詢、載入頁面 4 次 |
| 被擋當下，30 分鐘窗口內的查詢量 | **87 個**（預算 90，**沒有超過**） |
| 被擋的是哪一個請求 | 自動重載頁面之後的**第一個**時段查詢（10/10），離頁面載入完成只有幾秒 |
| 前一次重載（16:58） | 同樣的流程，沒有被擋 |
| 回應 | 一樣是 `429`、`{"error":"TOO_MANY_REQUESTS"}`、沒有 `Retry-After` |

- 「窗口內 ≤ 90 個就不會被擋」**不成立**。
- 被擋的位置剛好是「重載後第一個查詢」。如果被擋的時間點與重載無關，剛好落在這個位置的機率約 1/120（30 輪 × 4 個查詢），不到 1%，
  所以我們**懷疑**與重載有關：一次重載約 61 個請求擠在幾秒內，其中多少真的走網路要看瀏覽器快取。但這只是 1 次觀察，**不是結論**。
- 也可能是更長時間窗口（例如每小時）的累積量：那個小時內的查詢量（約 175 個）跟前一次乾淨的 61 分鐘（176 個）幾乎一樣，單看查詢量分不出來。
- 為了下次能判斷，程式現在會：每次載入頁面都記一筆（含有多少資源實際走網路），
  被擋時記下「距離上次載入頁面幾秒」與窗口內查詢量（存在 `state.blocks[].startStats`）。

**目前推論（仍是推論，不是伺服器公開的規則）**：
- 被擋後會**固定鎖定約 26～29 分鐘**：目前只有一次完整量測（25.3 分鐘仍被擋、29.4 分鐘已恢復），17:41 這一波會再量一次。
  若封鎖只是「窗口內的量降到門檻以下就解除」，停止查詢約 5 分鐘就該恢復，但實測 25 分鐘仍被擋，所以更像是固定時間的處罰。
- 觸發條件**不是**簡單的「30 分鐘內 N 個查詢」：129 個會被擋、87 個也會被擋（發生在重載後第一個查詢），另一段 88 個則沒事。
  可能的解釋，現有資料無法區分：(A) 重載頁面造成的短時間請求突發；(B) 更長時間窗口（例如每小時）的累積量；(C) 查詢加上頁面載入請求的合計。
- 只有一個身分、一天的樣本，沒有任何一個速率可以保證安全。

**還不知道的**：身分由哪個東西承載（`HttpOnly` Cookie？別的？）；「被自動化工具控制的分頁」是否被另外對待；
觸發的是「突發」還是「累積」。

**因此程式的策略**：第一次被擋後先暫停約 25 分鐘（`blockedWaitMs`；累積紀錄後改用「已知最短封鎖 × 0.9」），
之後每 2 分鐘只送 1 個請求試探（`blockedRetryMs`）；恢復後把這波實際持續多久記進 `state.blocks`。
封鎖期間如果重新貼程式或重新整理頁面，會**補回原本排定的等待時間**，不會只冷卻 2 分鐘就去試探（這個漏洞是 17:41 之後才補上的）。

**無論哪個假設成立，正確的做法都一樣：降低送出的請求量。** 所以程式內建了：

1. **查詢預算（滾動視窗）**：預設「30 分鐘最多 60 個查詢」（約每分鐘 2 個，4 天 = 每 2 分鐘一輪）。依實測：窗口內累積 129 個時被擋；
   90 個上限跑了 126 分鐘後，在 87 個時仍被擋 → 預設從 90 降到 60。
   超過就先等舊的查詢過期再送；被 429 時依當下窗口內的查詢量自動調降（× 0.7，只降不升）。
   面板會顯示 `📊 查詢預算 已用/上限`。這個機制同時是個實驗：60 個是否安全，還沒有證據。
2. **很少重載頁面**：預設沿用同一頁，每 120 輪（約 4 小時）才整頁重載一次（一次重載 ≈ 61 個請求）；頁面出問題時仍會立刻重載。
3. **休息下限預設 30 秒**（舊預設 10 秒約 20～30 分鐘就被擋）。
4. **被擋時每次記錄診斷資訊**：回應標頭名稱、`Retry-After`／`X-RateLimit-*`、內容前 120 字、
   本次執行以來的查詢總數與近 1／10／30 分鐘的數量、距離上次載入頁面幾秒。日後就能用真實數字判斷門檻，而不是猜。

> 我們**沒有**、也不會加入「被擋時自動清 Cookie／換身分／自動重開瀏覽器來繞過限流」這類功能。那是在規避網站的保護機制，
> 而且就算有效，也只是掩蓋「送太多了」這個根本問題。`scripts/` 裡的[重開 Chrome 小工具](#重開-chrome-小工具手動執行)
> 只在你手動執行時才會動，監控程式不會呼叫它（測試會檢查）。

**降低被限流機率的建議**：
1. 保持預設的 `interval.floor`（30 秒）與 `budget`；不要為了「快一點」把它們調到極限。
2. `days` 一次不要超過 7 天。
3. 保持 `reloadEvery` 為預設的 120（不要設成 1）。
4. 不要同時開多個分頁或多台電腦監控同一個網站。

## End-user 注意事項

> 請務必讀完。

1. **請保持分頁開啟、電腦不睡眠。** 關掉分頁、關機、合上螢幕睡眠，監控都會停止。
2. **有票後請自己盡快到網站下單。** 本工具不會幫你訂票，票也可能在你看到通知的當下已被搶走。
3. **請勿把頻率調到極限。** 頻繁請求可能造成：被限流（429）、被暫時封鎖 IP，甚至影響你正常訂票。
4. **不要繞過網站的防護。** 本專案刻意不偽造 `X-Schedule-Token`；請勿改成繞過防機器人驗證的版本。
5. **遵守網站服務條款與當地法規。** 僅限**個人自用監看**；請勿用於黃牛、轉售、大量搶票或影響他人購票。
6. **隱私**：腳本只在你的瀏覽器執行，不會把任何資料傳到第三方。歷史紀錄僅存在你的 `localStorage`。
7. **從不明來源貼到 Console、或安裝成使用者腳本的程式碼都有風險**：請先自行閱讀 `watcher.js`（有完整註解），確認無誤再貼上或安裝。
   使用者腳本會在符合網址的每一次頁面載入時自動執行，所以 `@match` 請保持盡量窄；本專案的 `.user.js` 已關閉自動更新。
8. **網站改版會失效**：若網站改了按鈕文字（`Next`）、時段文字格式（`입장`／`剩余`）或流程，需要對應修改。
9. **語系**：目前依賴中文版頁面的文字（`Next`、`剩余`）。其他語系頁面需調整選擇邏輯。
10. **通知限制**：預設僅標題＋面板；分頁在背景時，請留意分頁標題變化，或開啟 `desktopNotification`。

## 常見問題與疑難排解

| 現象 | 可能原因 | 處理 |
|---|---|---|
| 面板顯示「失敗: … 無資料（可能被限流）」 | 被限流（429／`요청실패`） | 腳本會自動暫停並退避；封鎖約 26～29 分鐘會自己解除。建議降低查詢速度（`rotate.everyMs` 調大）、縮小 `days`。 |
| 一直讀不到時段 | 月份／日期設錯、該月份尚未開放預訂、網路慢 | 確認 `month`／`days`；把 `waitAfterDayClick` 調大到 4000～5000。 |
| 面板顯示「被網站限流(429)，暫停到 HH:MM」 | 請求太密，網站限流 | 什麼都不用做，程式會在時間到後自動只送 1 個請求試探並恢復。可考慮調高 `interval.floor`。 |

## 已知限制

- 只能在**開著的分頁**中運作，不是背景服務；無法在電腦關機時通知你。瀏覽器也不允許網頁阻止電腦「關機／合蓋睡眠」，`keepAwake` 只能降低閒置睡眠的機率。
- 分頁若長時間在**背景**，Chrome 會限制計時器頻率，導致整體變慢；請保持前景或獨立視窗。
- 每輪都要重新載入頁面並逐日點擊，**耗時與天數成正比**（約每天 3～5 秒）。
- 依賴頁面 DOM 文字格式，網站改版就可能失效。
- 限流門檻不公開，**目前也沒有任何速率被證明安全**：實測 129 個/30 分鐘被擋、87 個/30 分鐘也被擋過（在重載頁面後），另一段 88 個/30 分鐘則連續跑了 2 小時。預設值是「目前最保守的猜測」，被擋時程式會暫停約 26 分鐘後自動再試，這段時間看不到票。
- 無法保證訂票成功；有票到下單之間仍有競爭。

## 開發歷程與實測結論

本專案是在實際使用中一步步收斂出來的，以下是踩過的坑（也是設計理由）：

1. **原本每 30 秒掃 22 天** → 短時間累積數百次查詢，觸發 **HTTP 429**，網站回 `요청실패`。
   → 改成只掃需要的日期、加入退避。
2. **嘗試直接呼叫 API** → 回 **403**，因為請求需要頁面產生的 `X-Schedule-Token`。
   → 決定**不繞過**，改回沿用 UI 流程。
3. **舊迴圈「復活」與新迴圈同時跑**，互相覆蓋狀態，造成假性 403。
   → 加入唯一 `RUN_ID` 與 `isAlive()` 檢查。
4. **失敗一次就永遠鎖死在較長間隔**。
   → 加入「在下限連續成功 N 次後放寬」的重新試探機制。
5. **間隔縮到 40 秒後不再縮短**（`40-20 < 30` 的邊界問題）。
   → 改為 `max(floor, interval - step)`，最後一級直接落到下限。
6. **整月 31 天＋休息 5 秒** → 第 3 輪被限流；證實自適應退避有效，並得到「不要太激進」的實測結論。

---

7. **v2：事件驅動重寫。** 一輪從約 23 秒縮到約 4～6 秒；改讀 HTTP 狀態碼與 JSON，精準分類錯誤；
   確認資料屬於被點的那一天；預設不再每輪重載頁面。
8. **持續 50 輪後又被限流**（每輪整頁重載約 9 個請求）。→ 發現每次載入頁面還要跑一次
   `challenge`／`issueToken`（工作量證明，token 有效 10 分鐘），改為沿用同一頁；
   被限流後改為暫停再試 1 個請求，而不是每幾十秒重試。（曾誤把「使用者重開 Chrome 的時間」當成「自己解除的時間」，已更正，見「限流」一節。）
9. **`resolve(jqXHR)` 陷阱**：見上節。
10. **加入查詢預算與診斷**：因為分不出限流的機制，改成「不論哪種機制都有效」的做法——控制總量；
    並讓每次被擋都留下可分析的數字。
11. **預算內仍被擋（17:41）**：預算 90 個/30 分鐘跑了 126 分鐘沒事，之後在窗口內只有 87 個時，於「自動重載頁面後的第一個查詢」被擋。
    → 「90 個以內安全」被推翻；預設預算降到 60、重載改成約 4 小時一次；每次載入頁面與每次被擋都留下更完整的紀錄；
    並補上一個漏洞：封鎖期間重新貼程式，原本只會冷卻 2 分鐘就去試探，現在會等到原本排定的時間。
    原因尚未確定（突發？累積？還是兩者合計？），見「限流」一節。
12. **輪流模式（溫和模式）**：把「每輪連查全部日期」改成「每次只查 1 天、日期輪流查」，消除一次連送 N 個請求的突發；
    平均量不變。各天結果合併成完整快照，提醒邏輯不變。這只是把請求排得更均勻，能否減少被擋仍待實測。
13. **使用者腳本誤報「找不到日曆」（2.1.1）**：用 AdGuard 安裝自動啟動版後，腳本在日曆被網頁畫出來之前就開始檢查，直接報錯。
    確認原始 HTML（約 56 KB）裡沒有 `Next` 也沒有年月標題，日曆是網頁的 JavaScript 事後產生的。→ 啟動時改成先等日曆出現（最多 30 秒），逾時才報錯；貼在 Console 時行為不變。
14. **設定 `everyMs` 卻沒有變快（2.1.2）**：預設預算 60 個/30 分鐘等於每 30 秒 1 個，所以只把 `everyMs` 改成 20 秒，實際仍是 30 秒。
    邏輯本來就是「取較慢者」，但面板沒說明、我的操作說明也漏了 `budget.maxCalls`。→ 面板現在會直接寫「設定是每 N 秒，但受查詢預算限制」，README 補上對照表。
