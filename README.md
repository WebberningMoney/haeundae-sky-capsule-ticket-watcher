# haeundae-sky-capsule-ticket-watcher 🎫

> 在「訂票頁面本身」持續監看指定日期的時段，一有票就用**分頁標題＋紅色面板**提醒你。
> 只監看，**不會下單、不會付款、不會填寫任何個資**。

**English summary** — A single-file browser-console script that polls a maketicket-style booking
page for released slots on chosen dates. It reloads a fresh copy of the page in a hidden
same-origin iframe every round, clicks the target dates, reads the rendered "remaining" text,
and flags any slot that is not sold out. It adapts its polling interval (shorten on success,
back off on failure) to stay under the site's rate limit. It does **not** bypass the site's
anti-bot token and never places orders.

## 它能做什麼／不能做什麼

| ✅ 能做 | ❌ 不做 |
|---|---|
| 定期重新載入並查詢指定日期的各時段剩餘數 | 自動下單、自動付款 |
| 有票時：標題變 `🎫有票! 10/11 5班10:30-11:00`、面板變紅 | 填寫姓名、電話、信箱、密碼等任何個資 |
| 記錄「什麼時間、發現哪天哪個時段、剩幾張」（存在瀏覽器） | 繞過網站的防機器人驗證（`X-Schedule-Token`） |
| 依成功／失敗自動調整查詢頻率，降低被限流的機率 | 在背景常駐（分頁關閉就停止） |
| （選用）瀏覽器桌面通知 | 保證一定搶得到票 |

## 快速開始（給完全沒有程式基礎的人）

> 全程只需要「複製、貼上、改兩個數字」，**不需要安裝任何東西**。大約 3 分鐘。

### 開始前的檢查表（請逐項打勾）

| ✔ | 項目 | 說明／怎麼做 |
|---|---|---|
| ☐ | 用**電腦版**瀏覽器 | 建議 Chrome。手機瀏覽器無法使用（沒有 Console）。 |
| ☐ | 電腦**接上電源**、網路穩定 | 監控要跑很久，沒電或斷網就會停。 |
| ☐ | 已打開**訂票頁**，並且看得到「預訂日期」日曆 | 網址通常長這樣：`https://…/ticket_chn/GDxxxxxxx`。**不是首頁、不是「我的訂單」頁**。 |
| ☐ | 這個分頁要**放在前景**（可以自己開一個獨立視窗） | 分頁被切到背景太久，瀏覽器會讓它變很慢，甚至停住。 |
| ☐ | 準備好要監看的**月份**和**日期** | 例如「10 月的 10 到 13 號」。 |
| ☐ | **不要**同時開多個監控 | 同一個分頁重複貼上會自動取代舊的，但多個分頁/多台電腦一起跑會讓網站更容易限流。 |

### 步驟

**步驟 1｜打開 Console（開發人員工具）**

| 系統 | 快捷鍵 |
|---|---|
| Mac | `⌥` + `⌘` + `J`（Option + Command + J） |
| Windows | `F12`，再點上方的 **Console** 分頁 |

> 會看到一個可以打字的區域，這就是 Console。**看到黃色警告或紅色字不用怕**，那是網站自己的訊息。

**步驟 2｜複製程式**
打開 [`watcher.js`](./watcher.js)，全選（`⌘A`／`Ctrl+A`）→ 複製（`⌘C`／`Ctrl+C`）。

**步驟 3｜改兩個地方（其他都不用動）**
先把程式貼到任何純文字編輯器（記事本、備忘錄、GitHub 網頁的編輯器都可以），找到最上方這一段：

```js
month: 10,        // ← ① 你要監看幾月（1~12）
...
days: '10-13',    // ← ② 你要監看幾號
```

- 只改**數字**，**不要刪掉**逗號 `,`、引號 `' '`、冒號 `:`。
- `days` 的寫法：`'10-13'`（10 到 13 號）、`'10,12,15-17'`（10、12、15~17 號）、`'25'`（只有 25 號）。
- **月份不用自己算按幾次 Next**，程式會自動看日曆現在是幾月，再自己切過去。

**步驟 4｜貼到 Console 並按 Enter**
回到瀏覽器 Console，貼上（`⌘V`／`Ctrl+V`），按 `Enter`。

> 🔒 **Chrome 的防貼上保護**：第一次貼可能出現提示，要你先輸入 `allow pasting` 並按 Enter，然後再貼一次。這是瀏覽器的安全機制，正常現象。

**步驟 5｜確認有啟動**
畫面右上角出現**黑色大字面板**，就代表成功了。之後：

- 面板**變紅**、分頁標題出現 `🎫有票!` → 有票了，**請立刻到網站下單**。
- 如果面板一開始就顯示 **⚠️ 無法啟動**，照上面的中文提示處理即可（例如「日期寫反了」、「這個頁面找不到日曆」）。點一下面板可以關掉它。

**停止**：在 Console 輸入 `window.__ticketWatcher.stop()` 按 Enter；或直接關掉這個分頁。

| Chrome 重啟後從頭摸索頻率 | ✅ 自動存檔、自動接續、必要時先冷卻 |
| 貼錯頁面、日期寫錯不知道哪裡錯 | ✅ 啟動前自動檢查，並用中文告訴你怎麼改 |
| 通知權限 | ✅ 若開啟 `desktopNotification`，啟動時自動請求一次 |

### 程式**無法**自動處理、需要你自己做的事

1. **打開正確的訂票頁**（程式不能替你決定要監看哪個商品）。
2. **貼上程式並按 Enter**（瀏覽器規定一定要由人操作）。第一次貼可能要先輸入 `allow pasting`。
3. **保持這個分頁在前景、電腦有電有網。** 瀏覽器不允許網頁程式阻止「整台電腦關機／合上螢幕睡眠」。
4. **Chrome 完全關閉重開後，需要重新貼一次**（或改用 Tampermonkey 自動啟動，見下方）。
5. **有票後，你要自己下單付款**，工具不會代勞。

## 設定參數

全部在 `watcher.js` 最上方的 `CONFIG`。**一般人只要改 `month` 和 `days` 兩個。**

| 參數 | 預設 | 說明 |
|---|---|---|
| `month` | `10` | **要監看幾月**（1~12）。程式會自動切換到該月，不用自己算按幾次 Next。 |
| `year` | `null` | 年份。`null` = 自動（沿用頁面顯示的年份；目標月份比目前顯示的早，就當作明年）。 |
| `days` | `'10-13'` | **要監看哪幾號**。可寫 `'10-13'`、`'10,12,15-17'`、`'25'` 或 `[10,11]`。建議一次不超過 7 天。 |
| `interval.start` | `60000` | 起始「每輪結束後的休息時間」（毫秒）。 |
| `interval.step` | `10000` | 每次成功縮短／失敗退回的幅度。 |
| `interval.floor` | `30000` | 休息時間下限（毫秒）。**越小越容易被限流**（舊預設 10000 約 20～30 分鐘就被擋）。 |
| `interval.max` | `180000` | 失敗退避時的上限。 |
| `interval.probeAfterOk` | `10` | 因失敗被鎖住的下限，需在該下限連續成功幾次才放寬一級。 |
| `initialDelay` | `0` | 啟動後先等多久再開始第一輪。剛被限流時可設 `240000`（4 分鐘）。 |
| `reloadEvery` | `30` | 每幾輪才整頁重新載入一次。設 `1` = 每輪都重載（請求量約多一倍，較容易被限流）。 |
| `blockedWaitMs` | `1500000` | 第一次被限流（429）後先暫停多久再送第一個試探（25 分鐘；依實測封鎖約 26～29 分鐘）。見「限流」一節。 |
| `blockedRetryMs` | `120000` | 第一個試探仍被擋時，之後每隔多久再試 1 個請求（2 分鐘）。 |
| `budget.windowMs` / `budget.maxCalls` | `30 分鐘` / `90` | 查詢預算：視窗內最多送幾個時段查詢。`maxCalls: null` = 不限制（不建議）。被擋時會自動調降。 |
| `budget.learnFactor` / `budget.min` | `0.7` / `30` | 被擋時，新預算 = 窗口內查詢量 × 0.7（不低於 30）。 |
| `timing.readyTimeoutMs` | `20000` | 等頁面載入並出現日曆的上限。網路慢就調大。 |
| `timing.ajaxTimeoutMs` | `12000` | 點日期後，等該次查詢回應的上限。 |
| `timing.jitter` | `400~1200` | 每天之間的隨機間隔，避免規律到像機器。 |
| `notify.*` | 全開 | 提醒方式，見下方「提醒設定」。 |
| `panel.fontPx` / `panel.widthPx` | `40` / `820` | 面板字體大小與寬度。 |
| `resume.*` | 開 | 中斷後自動接續（見下節）。 |
| `keepAwake` | `true` | 自動要求瀏覽器保持螢幕喚醒（不能阻止電腦關機／合蓋睡眠）。 |
| `workerTimers` | `true` | 用 Web Worker 計時，降低分頁在背景被 Chrome 節流的影響；失敗會自動退回一般計時。 |
| `allowMultipleTabs` | `false` | 是否允許多個分頁同時監控（不建議）。 |
| `maxHistory` | `200` | 歷史紀錄最多保留幾筆。 |

## 提醒設定（桌面版 Chrome：macOS／Windows）

有「新出現」的票時，會同時觸發下列提醒（都可以在 `CONFIG.notify` 個別關掉）：

| 提醒 | 說明 |
|---|---|
| 🖥 系統通知 | 出現在 macOS 通知中心／Windows 動作中心，會一直停留到你點掉（`requireInteraction`）。點通知會直接帶你回到此分頁。 |
| 🔔 提示音 | 用 Web Audio 合成，不需要任何音檔。你沒在看螢幕時，每 6 秒再響一次，最多持續 3 分鐘。 |
| 🗣 語音 | 溫柔女聲念「有票囉，請盡快前往訂票」。預設自動挑台灣國語女聲（macOS：Meijia → Sandy → Shelley → Flo；Windows：HanHan／Yating；備援 Google 國語（臺灣））。可用 `notify.voice.name` 指定，`rate`／`pitch` 調語速與音調。 |
| ✨ 標題閃爍 | 分頁標題在 `🎫有票! …` 與 `🔔🔔 有票了！ …` 之間交替，切在別的分頁也看得到。 |
| 🔴 分頁圖示紅點 | 分頁的小圖示變成紅點驚嘆號。 |
| 🟥 面板變紅 | 只要仍有票，面板就保持紅色，並列出所有日期／時段／剩餘數。 |

**你看到了就會自動停止吵人**：點一下頁面、按任何鍵、或切回此分頁，聲音與閃爍就會停止（面板仍會保持紅色）。

### 第一次使用，請做這兩件事（各只要一次）

1. **在頁面上任意點一下。** Chrome 規定網頁必須先被使用者操作過才能出聲。面板最後一行會顯示 `🔊 提示音與語音：🔇 尚未啟用（請在頁面上點一下）`，點過之後變成 `✅ 已啟用`。
2. **允許通知。** 面板倒數第二行顯示 `🔔 桌面通知：✅ 已開啟` 才代表可用；若是 `❌ 被封鎖`（或 `❓ 尚未允許`）：
   - Chrome：網址列左側的 🔒 → **網站設定** → **通知** → 改成**允許**。
   - **macOS**：系統設定 → 通知 → Google Chrome → 允許通知；並**關閉「專注模式」／勿擾**。
   - **Windows**：設定 → 系統 → 通知，開啟通知；並**關閉「專注助理」**。

### 先測試再開始

在 Console 執行 `window.__ticketWatcher.testAlert()`，會模擬一次「有票」：你應該會看到通知、聽到提示音與語音、看到標題閃爍與紅點。點一下頁面即可停止。**建議每次開始長時間監控前先測一次。**

> 語音的可用聲音因電腦而異。查看清單：`speechSynthesis.getVoices().map(v => v.name + ' | ' + v.lang)`。
> 本工具只使用系統／瀏覽器內建的合成語音，不提供也不模仿特定真人的聲音。

## 運作原理（詳細）

### 整體流程

```
  ┌───────────────────────── 每一輪 ─────────────────────────┐
  │ 1. 需要時才建立隱藏 iframe → 載入全新訂票頁               │
  │    （預設每 30 輪，或失敗後）                             │
  │ 2. 用 jQuery.active 等頁面「閒置」，再自動切到目標月份     │
  │ 3. 逐日：點日期 → 旁聽網站自己發的時段查詢                 │
  │      ・以請求裡的 sdDate 確認是「這一次點擊」的回應         │
  │      ・直接拿 HTTP 狀態碼 + JSON（sdName／sdRemainder）    │
  │ 4. sdRemainder > 0 即有票；與上一輪比對，只提醒「新出現」  │
  │ 5. 依結果調整休息時間 → 休息 → 下一輪                     │
  └────────────────────────────────────────────────────────────┘
```

### 事件驅動（v2 的核心改進）

舊版靠「固定等 3 秒再讀畫面」，慢又不可靠：慢的請求可能讀到上一天的舊資料，
而「讀不到文字」也分不出是被限流還是別的原因。v2 改成：

- **等到才往下走**：頁面閒置、月份真的換了、這次點擊的回應真的回來，才繼續。
  一輪從約 23 秒縮短到約 4～6 秒，偵測延遲大幅降低。
- **確認資料屬於被點的那一天**：比對請求裡的 `sdDate`；收到別天的資料會判為 `stale` 並重試。
- **精準的錯誤分類**：直接讀 HTTP 狀態碼，見下表。
- **JSON 為主、畫面為輔**：讀得到 JSON 就用 JSON（已實測與畫面文字逐筆一致）；
  API 格式改變時自動退回讀畫面文字。

### 錯誤分類

| 種類 | 觸發 | 處理 |
|---|---|---|
| `rate_limit` | HTTP 429 | **硬失敗**：退回上一級並鎖定下限；先暫停 `blockedWaitMs`（預設 25 分鐘），之後每 `blockedRetryMs`（2 分鐘）只送 1 個請求試探；有 `Retry-After` 就照做；發桌面警示 |
| `blocked` | HTTP 403 | 同上 |
| `server` | HTTP 5xx | 同上 |
| `load` | 頁面載入逾時／日曆沒出現 | 同上（多半是被暫時擋住） |
| `timeout` `stale` `network` | 等不到回應／收到別天資料／網路錯誤 | **軟失敗**：間隔不變，下一輪重新載入頁面再試 |
| `notopen` | 切不到目標月份 | 該月份可能尚未開放，面板顯示提示並持續等待（不會停止） |
| `layout` | 找不到日曆／按鈕 | 連續 3 次就停止並提示「網站可能改版」 |
| （非失敗）該日無場次 | 200 且資料為空 | 記為「無場次」，不算錯誤 |

### 為什麼不直接呼叫 API？

網站發時段查詢前，頁面會先跑一段**工作量證明（proof-of-work）**：
`/ticket/challenge` → 計算 → `/ticket/issueToken`，取得一個**有效 10 分鐘**的 token，
放在 `X-Schedule-Token` 標頭。這是防機器人機制，直接呼叫會被 403。
本專案**刻意不偽造它**：仍由頁面自己發請求，我們只在 `ajaxComplete` 事件「旁聽」結果，
並且主動降頻。請勿修改成繞過防護的版本。

### 為什麼預設不再每輪重載頁面？

每次載入頁面，都會多出：頁面本身、`challenge`、`issueToken`、月份清單等請求（實測約 5 個），
而且要重算一次工作量證明。網站的 token 有效 10 分鐘，過期時頁面會自己換新的，
所以**沿用同一頁一樣拿得到最新資料**（每次點日期都會向伺服器查詢）。
實測第 2 輪起每輪只有 4 個請求（每天 1 個）。

### 有票怎麼判斷？

API 每個時段回傳 `sdName`（如 `20회차(18:00 ~ 18:30) 입장`）與 `sdRemainder`（剩餘數）。
`sdRemainder > 0` 就是有票。備援模式下則讀畫面文字 `[剩余:N]`，「售罄」不含數字所以不會匹配。

### 為什麼要攔截 `alert`？

請求失敗時網站會 `alert('요청실패')`。alert 會**阻塞整個分頁**，導致自動化卡死。
腳本在 iframe 載入期間持續把 `alert` 換成「只記錄、不彈窗」的函式（記錄最多保留 50 筆）。

### 如何避免「新票重複通知」？

用 `日期|時段名稱` 當 key，保存上一輪有票的 key 集合，**這一輪有、上一輪沒有**的才算新增。
這份集合也會存進接續存檔：Chrome 中斷不久就重啟，不會重複通知；中斷很久，仍存在的票會重新提醒一次。

### 如何避免多個迴圈／多個分頁同時跑？

- 同一分頁：每次啟動產生唯一 `RUN_ID`，舊迴圈每一步都檢查，發現不是自己就退出。
- 多個分頁：用 `localStorage` 心跳（每 10 秒，Worker 計時）偵測；超過 90 秒沒有心跳就視為對方已不在。
  另一個分頁真的在監控時，新的會拒絕啟動並用中文說明。重新整理或關閉分頁時會主動釋放鎖（`pagehide`），
  所以重新整理後可以立刻重新啟動；只有瀏覽器當機這類意外情況才需要等最多 90 秒。

### 計時器與背景分頁

優先使用 **Web Worker 計時**：Chrome 對背景分頁會把主執行緒的計時器降到每分鐘一次，
Worker 不受同樣限制。若網站的安全設定不允許 Worker，會自動退回一般計時（啟動記錄會註明）。
> 注意：這只保證「程式的排程」不被拖慢；分頁完全被隱藏時，瀏覽器仍可能降低頁面本身的效能，
> 所以仍建議把此分頁放在前景或獨立視窗。

## 中斷後自動接續（Chrome 重啟／分頁重開）

監控程式活在分頁的記憶體裡，**Chrome 重啟、分頁被關掉或重新整理，程式就會消失**。
為了不必每次都從頭摸索，程式會在**每一輪結束後**把以下資訊存進 `localStorage`
（鍵名 `__ticket_watcher_state`）：

- 目前學到的休息間隔、生效的下限、退回用的間隔堆疊
- 已完成輪數、在下限連續成功的次數
- 上次是否以失敗收尾、存檔時間

重新啟動時：

| 情況 | 行為 |
|---|---|
| 沒有存檔，或存檔超過 24 小時 | 從 `interval.start` 重新開始 |
| 有存檔，且中斷時間短（< 10 分鐘）且上次成功 | 直接沿用學到的間隔繼續 |
| 有存檔，但中斷過久（> 10 分鐘）**或**上次以失敗收尾 | 沿用間隔，但**先冷卻 2 分鐘**再開始，避免一啟動就撞上尚未解除的限流 |

想清掉存檔重新開始：`window.__ticketWatcher.resetSaved()`，再重新貼上腳本。

**想讓它在分頁一開就自動啟動？** 檔案最前面已附 `// ==UserScript==` 標頭，
安裝 Tampermonkey／Violentmonkey 後把整份檔案存成使用者腳本即可
（`@match` 預設為 `https://*/ticket_chn/*`，請依需要收窄成你的網站）。
> 程式開頭已內建 `if (window.top !== window.self) return;`，只會在最上層視窗執行，
> 不會在腳本自己建立的隱藏 iframe 裡重複啟動（否則會遞迴失控）。

## 自適應間隔與限流

「休息時間」= 一輪**結束後**到下一輪**開始前**的等待。實際週期 ≈ 一輪耗時（約 4～6 秒）＋ 休息時間。

| 事件 | 行為 |
|---|---|
| 一輪成功 | 休息時間縮短一級（`step`），直到下限 |
| 硬失敗（429／403／5xx／載入失敗） | 退回**上一個用過的休息時間**並把它設為新下限；並暫停後只送 1 個請求試探（見上表） |
| 軟失敗（逾時／舊資料／網路） | 間隔不變，下一輪重新載入頁面再試 |
| 連續失敗 | 等待時間再乘倍數（最多 5 倍）；伺服器有給 `Retry-After` 就以較長者為準 |
| 在下限連續成功 10 次 | 才把「因失敗而抬高的下限」放寬一級，小心重新試探 |
| 限流解除 | 記錄「這波限流持續了幾分鐘」（`state.blocks`），並在記錄裡註明 |

### 限流：已知的事實、我們的推論、還不知道的事

網站對「時段查詢」（`getDateScheduleList`）有限流，超過會回 **HTTP 429**，內容是
`{"error":"TOO_MANY_REQUESTS"}`。以下把**觀察到的事實**和**推論**分開寫。

**已確認的事實**

| 事實 | 依據 |
|---|---|
| 被擋的只有「時段查詢」，同一時間月份清單等其他請求仍是 200 | 實際擷取到回應 |
| 被擋時就算剛換了全新的 token（`challenge`→`issueToken` 都成功），時段查詢仍是 429 | 同上 |
| 載入一次頁面 = **約 61 個請求**（約 50 個靜態檔案＋第三方腳本＋4 個 XHR）；一輪查詢只有 4 個 | 讀取 iframe 的 `performance` 紀錄 |
| 頁面沒有偷偷多發時段查詢：每 83 秒的 XHR 剛好 = 1 個 challenge + 1 個 issueToken + 1 個月份清單 + 每輪 4 天 | 同上 |
| 每次被擋，都在連續輪詢約 20～30 分鐘、送出數百個請求之後 | 執行記錄（估計值） |
| **每一次恢復，都發生在「使用者重開 Chrome」之後**；我們沒有任何一次「不重開、自己恢復」的紀錄 | 4 次事件的時間軸 |
| 重開 Chrome 後，網站的 `localStorage`（存檔）會是空的 | 連續 3 次重開都觀察到 |
| 頁面上 JavaScript 看得到的 Cookie 只有一個 `SCOUTER`（效能監控用），看不到 session／登入 Cookie | `document.cookie`（`HttpOnly` Cookie 本來就看不到，所以**不能因此斷定沒有**） |
| 部分使用者的電腦裝有廣告／內容過濾軟體（頁面資源紀錄中可見被注入的本機腳本），瀏覽器流量會先經過它；這可能影響連線與請求行為，是排查時需要留意的環境因素 | 頁面資源紀錄 |

**曾經寫錯、現在更正的說法**

> 舊版 README 曾寫「限流約 6～9 分鐘自動解除，所以重開 Chrome 不是功勞」。**這個結論不成立。**
> 當初只是發現「恢復時間都落在 6～9.5 分鐘」，但那些恢復時間本來就是「使用者重開 Chrome 的時間」，
> 並不是「自己解除的時間」，沒有任何一次是不重開就恢復的。所以只能說：**目前分不出是「時間到了自己解除」還是「重開 Chrome 讓伺服器認不得你」**。

**實驗紀錄（2026-09-29）：封鎖大約持續 26～29 分鐘，會自己解除**

| 時間 | 距第一次 429 | 視窗／動作 | 結果 |
|---|---|---|---|
| 14:21:36 | 0 | 一般視窗（監控中，本次已送 129 個查詢） | 429 |
| 約 14:22–14:24 | 約 1～3 分 | **無痕視窗**（使用者手動點一次） | 正常 |
| 14:25:00 | 3.4 分 | 一般視窗（對照，1 個請求） | 429 |
| 14:37:53 | 16.3 分 | 一般視窗（新載入頁面、新 token、1 個請求） | 429 |
| 14:43:55 | 22.3 分 | 一般視窗的**全新分頁**（1 個請求） | 429 |
| 14:46:54 | 25.3 分 | 自動試探（1 個請求） | 429 |
| **14:51:02** | **29.4 分** | 同一個分頁、**沒有重開瀏覽器** | **正常** |

- **封鎖是暫時的**：25.3 分鐘仍被擋、29.4 分鐘已恢復，沒有做任何處置。中間送了 5 次被擋的試探／對照請求，
  也沒有延長封鎖（最後一次被擋後過 4 分鐘就解除）。
- **新載入頁面、換新 token、開新分頁都沒有用**，只是時間到了才解除。
- 被擋的**當下**，無痕視窗是正常的 → 封鎖綁在某種「用戶端身分」，不是全站或整個 IP。
  但當時無痕視窗同時也「沒有 Cookie」、「沒有被自動化工具控制」，這兩個因素還沒有拆開。
- 伺服器的 429 只有 `{"error":"TOO_MANY_REQUESTS"}`，**沒有 `Retry-After`、沒有任何限流標頭**。
- 網站的取 token 腳本不碰 Cookie／`localStorage`／`sessionStorage`／`IndexedDB`，也沒有瀏覽器指紋；
  前端 JS 沒有偵測自動化的關鍵字，`navigator.webdriver` 為 `false`。所以身分是**伺服器端**用瀏覽器自動帶上的東西認的（JS 看不到）。

**曾寫錯又更正的兩個結論**
1. 「限流約 6～9 分鐘自動解除」：當時的「恢復時間」其實是使用者重開 Chrome 的時間。
2. 「至少 16～22 分鐘不會自己解除，重開才有用」：只是當時還沒等到，實際約 26～29 分鐘就會解除。
   **重開 Chrome 或換無痕視窗只是「更早換成新的身分」的捷徑，不是必要的。**

**後續觀察（同一天稍晚）**：改成「查詢預算 30 分鐘 90 個、每輪平均分散」之後，連續執行 **61 分鐘、共 176 個時段查詢（平均每分鐘 2.9 個，任何 30 分鐘窗口內最多約 88～90 個）都沒有再被擋**。
對照被擋那次：30 分鐘窗口內累積 129 個（18 分鐘內送出，約每分鐘 7 個）。

**目前推論（仍是推論，不是伺服器公開的規則）**：
- 每個用戶端身分有一個「30 分鐘窗口內的查詢量門檻」，落在 **90 到 129 個之間**。
- 超過門檻會被**固定鎖定約 26～29 分鐘**（很可能是 30 分鐘）。若封鎖只是「窗口內的量降到門檻以下就解除」，
  被擋後停止查詢約 5 分鐘就該恢復，但實測 25 分鐘仍被擋，所以更像是固定時間的處罰。
- 「累計總量」不是關鍵：這個身分在 61 分鐘內已累計 176 個查詢（比被擋那次的 129 個多）仍未被擋，所以看的是「速率／窗口」。
- 只有一個小時、一個身分的樣本，沒有證明「90 個一定安全」，只能說目前沒有再被擋。

**還不知道的**：身分由哪個東西承載（`HttpOnly` Cookie？別的？）；「被自動化工具控制的分頁」是否被另外對待；
被擋前的門檻是總量還是速率。

**因此程式的策略**：第一次被擋後先暫停約 25 分鐘（`blockedWaitMs`；累積紀錄後改用「已知最短封鎖 × 0.9」），
之後每 2 分鐘只送 1 個請求試探（`blockedRetryMs`）；恢復後把這波實際持續多久記進 `state.blocks`。

**無論哪個假設成立，正確的做法都一樣：降低送出的查詢量。** 所以程式內建了：

1. **查詢預算（滾動視窗）**：預設「30 分鐘最多 90 個查詢」（約每分鐘 3 個）。依實測：窗口內累積 129 個時被擋；改用 90 個上限後連續跑了 60 分鐘以上（176 個查詢）沒有被擋。
   超過就先等舊的查詢過期再送；被 429 時依當下窗口內的查詢量自動調降（× 0.7，只降不升）。
   面板會顯示 `📊 查詢預算 已用/上限`。這個機制同時是個實驗：若照預算跑仍然被擋，就表示假設 B 不成立。
2. **預設沿用同一頁**，不再每輪整頁重載（一次重載 ≈ 61 個請求）。
3. **休息下限預設 30 秒**（舊預設 10 秒約 20～30 分鐘就被擋）。
4. **被擋時每次記錄診斷資訊**：回應標頭名稱、`Retry-After`／`X-RateLimit-*`、內容前 120 字、
   本次執行以來的查詢總數與近 1／10／30 分鐘的數量。日後就能用真實數字判斷門檻，而不是猜。

> 我們**沒有**、也不會加入「被擋時自動清 Cookie／換身分來繞過限流」這類功能。那是在規避網站的保護機制，
> 而且就算有效，也只是掩蓋「送太多了」這個根本問題。

**降低被限流機率的建議**：
1. 保持預設的 `interval.floor`（30 秒）與 `budget`；不要為了「快一點」把它們調到極限。
2. `days` 一次不要超過 7 天。
3. 保持 `reloadEvery` 為預設的 30（不要設成 1）。
4. 不要同時開多個分頁或多台電腦監控同一個網站。

## End-user 注意事項

> 請務必讀完。

1. **請保持分頁開啟、電腦不睡眠。** 關掉分頁、關機、合上螢幕睡眠，監控都會停止。
2. **有票後請自己盡快到網站下單。** 本工具不會幫你訂票，票也可能在你看到通知的當下已被搶走。
3. **請勿把頻率調到極限。** 頻繁請求可能造成：被限流（429）、被暫時封鎖 IP，甚至影響你正常訂票。
4. **不要繞過網站的防護。** 本專案刻意不偽造 `X-Schedule-Token`；請勿改成繞過防機器人驗證的版本。
5. **遵守網站服務條款與當地法規。** 僅限**個人自用監看**；請勿用於黃牛、轉售、大量搶票或影響他人購票。
6. **隱私**：腳本只在你的瀏覽器執行，不會把任何資料傳到第三方。歷史紀錄僅存在你的 `localStorage`。
7. **從不明來源貼到 Console 的程式碼都有風險**：請先自行閱讀 `watcher.js`（有完整註解），確認無誤再貼上。
8. **網站改版會失效**：若網站改了按鈕文字（`Next`）、時段文字格式（`입장`／`剩余`）或流程，需要對應修改。
9. **語系**：目前依賴中文版頁面的文字（`Next`、`剩余`）。其他語系頁面需調整選擇邏輯。
10. **通知限制**：預設僅標題＋面板；分頁在背景時，請留意分頁標題變化，或開啟 `desktopNotification`。

## 常見問題與疑難排解

| 現象 | 可能原因 | 處理 |
|---|---|---|
| 面板顯示「失敗: … 無資料（可能被限流）」 | 被限流（429／`요청실패`） | 腳本會自動退避；持續失敗請等 10～30 分鐘，或重啟瀏覽器，並調高 `floor`、縮小 `days`。 |
| 一直讀不到時段 | 月份／日期設錯、該月份尚未開放預訂、網路慢 | 確認 `month`／`days`；把 `waitAfterDayClick` 調大到 4000～5000。 |
| 面板顯示「被網站限流(429)，暫停到 HH:MM」 | 請求太密，網站限流 | 什麼都不用做，程式會在時間到後自動只送 1 個請求試探並恢復。可考慮調高 `interval.floor`。 |
| 面板顯示 `🔔 桌面通知：❌ 被封鎖` | Chrome 或系統封鎖了通知 | 見「提醒設定」的兩個步驟。改完設定後約 5 秒內面板會自動更新，不必重新整理。 |
| 明明允許了通知，面板仍顯示被封鎖（舊版問題） | 舊版用 `Notification.permission` 判斷，這個值在部分環境會一直回報 `denied`，即使實際是允許的 | v2 已改用 `navigator.permissions.query` 為準，並實測過真的能送出通知。若你仍看不到系統通知，請檢查 macOS「系統設定 → 通知 → Google Chrome」與「專注模式」。 |
| 面板顯示 `🔊 提示音與語音：🔇 尚未啟用` | Chrome 規定要先有人操作過頁面才能出聲 | 在頁面任意處點一下。 |
| 沒聽到語音 | 網路語音需要連網；或系統沒有該聲音 | 斷網時會自動改用本機女聲；也可在 `notify.voice.name` 指定其他聲音。 |
| 面板顯示「⚠️ 無法啟動：另一個分頁已經在監控」 | 已有另一個分頁在跑 | 關掉另一個，或（不建議）把 `allowMultipleTabs` 設為 `true`。 |
| 面板顯示「面板變紅、提示 ⚠️ 已停止」 | 連續 3 次找不到日曆元素（網站可能改版） | 確認頁面是訂票頁；若網站改版，需要更新腳本。 |
| 面板顯示「⚠️ 無法啟動」 | 啟動前檢查沒通過（貼錯頁面、日期寫錯…） | 照面板上的中文提示修正後重貼。點一下面板可關閉。 |
| 面板下方出現「⚠ 分頁在背景」 | 此分頁被切到背景／被遮住，瀏覽器讓它變慢 | 把此分頁拉到前景，或拖出成獨立視窗。 |
| 顯示「切不到 X 月」 | 該月份還沒開放預訂，日曆按不到那個月 | 改成已開放的月份，或等開放後再跑。 |
| 面板沒出現 | 貼到錯誤的分頁／Console 選到 iframe 環境 | 確認在訂票頁的**最上層**（Console 左上角 context 選 `top`）。 |
| 貼上被拒 | Chrome 防貼上保護 | 先在 Console 輸入 `allow pasting`，再貼。 |
| 重新整理後監控消失 | 腳本存在頁面記憶體中 | 重新貼上（歷史紀錄會保留）。用 Tampermonkey 可自動執行。 |
| 出現 `403` | 有人嘗試直接呼叫 API（缺少 `X-Schedule-Token`） | 不要直接呼叫 API；使用本腳本的 UI 流程。 |
| 標題沒變、面板沒紅，但你在別處看到有票 | 該時段在兩輪之間才釋出／又被搶走 | 縮短休息時間（注意限流風險）。 |

## 已知限制

- 只能在**開著的分頁**中運作，不是背景服務；無法在電腦關機時通知你。瀏覽器也不允許網頁阻止電腦「關機／合蓋睡眠」，`keepAwake` 只能降低閒置睡眠的機率。
- 分頁若長時間在**背景**，Chrome 會限制計時器頻率，導致整體變慢；請保持前景或獨立視窗。
- 每輪都要重新載入頁面並逐日點擊，**耗時與天數成正比**（約每天 3～5 秒）。
- 依賴頁面 DOM 文字格式，網站改版就可能失效。
- 限流門檻不公開，實測值僅供參考，可能隨時間或流量變化。
- 無法保證訂票成功；有票到下單之間仍有競爭。

## 開發者：專案結構與測試

```
ticket-watcher/
├─ watcher.js          # 主程式（單一檔案，貼到 Console 即可；含 UserScript 標頭）
├─ test/core.test.js   # 核心邏輯的單元測試
├─ package.json        # 只有 npm test 指令，沒有任何依賴
├─ README.md
└─ LICENSE
```

- `watcher.js` 分成兩層：**核心邏輯**（`Core`：日期解析、月份計算、HTTP 分類、Retry-After、
  有票判斷、新票比對、自適應間隔控制器…，全是不碰 DOM 的純函式）與**瀏覽器層**（iframe、事件監聽、面板、提醒…）。
- 在 Node 載入時（沒有 `window`）只匯出 `Core`，所以可以直接單元測試：

```bash
npm test          # 或： node --test
```

目前 21 個測試，涵蓋：日期各種合法／錯誤寫法、月份差計算（含跨年、往前切）、HTTP 狀態分類、
`Retry-After`（秒數／日期／過期）、有票判斷（字串數字）、新票偵測（持續有票不重複、消失再出現算新增）、
存檔鍵隔離、間隔控制器（縮短到下限、硬失敗退一級並鎖定、放寬下限、軟失敗、加倍與上限、存檔還原容錯）。

> 瀏覽器層（iframe、`ajaxComplete` 旁聽、通知、語音）需要真實頁面，無法在 Node 測。
> 開發時曾因此抓到一個單元測試不可能發現的 bug：`jqXHR` 是類 Promise 物件，直接 `resolve(xhr)` 會被自動拆開，
> 導致拿不到狀態碼。這類問題只能在真實網站上驗證。

## 開發歷程與實測結論

本專案是在實際使用中一步步收斂出來的，以下是踩過的坑（也是設計理由）：

1. **原本每 30 秒掃 22 天** → 短時間累積數百次查詢，觸發 **HTTP 429**，網站回 `요청실패`。
   → 改成只掃需要的日期、加入退避。
2. **嘗試直接呼叫 API** → 回 **403**，因為請求需要頁面產生的 `X-Schedule-Token`。
   → 決定**不繞過**，改回沿用 UI 流程。
3. **舊迴圈「復活」與新迴圈同時跑**，互相覆蓋狀態，造成假性 403。
   → 加入唯一 `RUN_ID` 與 `isAlive()` 檢查。
4. **失敗一次就永遠鎖死在較長間隔**。
   → 加入「在下限連續成功 N 次後放寬」的重新試探機制。
5. **間隔縮到 40 秒後不再縮短**（`40-20 < 30` 的邊界問題）。
   → 改為 `max(floor, interval - step)`，最後一級直接落到下限。
6. **整月 31 天＋休息 5 秒** → 第 3 輪被限流；證實自適應退避有效，並得到「不要太激進」的實測結論。

---

7. **v2：事件驅動重寫。** 一輪從約 23 秒縮到約 4～6 秒；改讀 HTTP 狀態碼與 JSON，精準分類錯誤；
   確認資料屬於被點的那一天；預設不再每輪重載頁面。
8. **持續 50 輪後又被限流**（每輪整頁重載約 9 個請求）。→ 發現每次載入頁面還要跑一次
   `challenge`／`issueToken`（工作量證明，token 有效 10 分鐘），改為沿用同一頁；
   被限流後改為暫停再試 1 個請求，而不是每幾十秒重試。（曾誤把「使用者重開 Chrome 的時間」當成「自己解除的時間」，已更正，見「限流」一節。）
10. **加入查詢預算與診斷**：因為分不出限流的機制，改成「不論哪種機制都有效」的做法——控制總量；
    並讓每次被擋都留下可分析的數字。
9. **`resolve(jqXHR)` 陷阱**：見上節。
