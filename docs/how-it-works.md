## 運作原理（詳細）

### 整體流程

```
  ┌───────────────────────── 每一輪 ─────────────────────────┐
  │ 1. 需要時才建立隱藏 iframe → 載入全新訂票頁               │
  │    （預設每 180 輪，或失敗後）                            │
  │ 2. 用 jQuery.active 等頁面「閒置」，再自動切到目標月份     │
  │ 3. 逐日：點日期 → 旁聽網站自己發的時段查詢                 │
  │      ・以請求裡的 sdDate 確認是「這一次點擊」的回應         │
  │      ・直接拿 HTTP 狀態碼 + JSON（sdName／sdRemainder）    │
  │ 4. sdRemainder > 0 即有票；與上一輪比對，只提醒「新出現」  │
  │ 5. 依結果調整休息時間 → 休息 → 下一輪                     │
  └────────────────────────────────────────────────────────────┘
```

### 事件驅動（v2 的核心改進）

舊版靠「固定等 3 秒再讀畫面」，慢又不可靠：慢的請求可能讀到上一天的舊資料，
而「讀不到文字」也分不出是被限流還是別的原因。v2 改成：

- **等到才往下走**：頁面閒置、月份真的換了、這次點擊的回應真的回來，才繼續。
  一輪從約 23 秒縮短到約 4～6 秒，偵測延遲大幅降低。
- **確認資料屬於被點的那一天**：比對請求裡的 `sdDate`；收到別天的資料會判為 `stale` 並重試。
- **精準的錯誤分類**：直接讀 HTTP 狀態碼，見下表。
- **JSON 為主、畫面為輔**：讀得到 JSON 就用 JSON（已實測與畫面文字逐筆一致）；
  API 格式改變時自動退回讀畫面文字。

### 錯誤分類

| 種類 | 觸發 | 處理 |
|---|---|---|
| `rate_limit` | HTTP 429 | **硬失敗**：退回上一級並鎖定下限；先暫停 `blockedWaitMs`（預設 25 分鐘），之後每 `blockedRetryMs`（2 分鐘）只送 1 個請求試探；有 `Retry-After` 就照做；發桌面警示 |
| `blocked` | HTTP 403 | 同上 |
| `server` | HTTP 5xx | 同上 |
| `load` | 頁面載入逾時／日曆沒出現 | 同上（多半是被暫時擋住） |
| `timeout` `stale` `network` | 等不到回應／收到別天資料／網路錯誤 | **軟失敗**：間隔不變，下一輪重新載入頁面再試 |
| `notopen` | 切不到目標月份 | 該月份可能尚未開放，面板顯示提示並持續等待（不會停止） |
| `layout` | 找不到日曆／按鈕 | 連續 3 次就停止並提示「網站可能改版」 |
| （非失敗）該日無場次 | 200 且資料為空 | 記為「無場次」，不算錯誤 |

### 為什麼不直接呼叫 API？

網站發時段查詢前，頁面會先跑一段**工作量證明（proof-of-work）**：
`/ticket/challenge` → 計算 → `/ticket/issueToken`，取得一個**有效 10 分鐘**的 token，
放在 `X-Schedule-Token` 標頭。這是防機器人機制，直接呼叫會被 403。
本專案**刻意不偽造它**：仍由頁面自己發請求，我們只在 `ajaxComplete` 事件「旁聽」結果，
並且主動降頻。請勿修改成繞過防護的版本。

### 為什麼預設不再每輪重載頁面？

每次載入頁面，都會多出：頁面本身、`challenge`、`issueToken`、月份清單等請求（實測約 5 個），
而且要重算一次工作量證明。網站的 token 有效 10 分鐘，過期時頁面會自己換新的，
所以**沿用同一頁一樣拿得到最新資料**（每次點日期都會向伺服器查詢）。
實測第 2 輪起每輪只有 4 個請求（每天 1 個）。

### 輪流模式（溫和模式，預設）

舊做法是每輪「連續」查全部日期（例如 4 天 = 一次連送 4 個請求，再休息一兩分鐘），這對伺服器來說是一個小突發。
輪流模式改成**每次只查 1 天**，日期輪流查：

- 平均請求量不變（預設每 20 秒 1 個 = 每分鐘 3 個），但不再有「一次連送 N 個」的突發。
- 每一天被檢查的頻率 = `rotate.everyMs` × 天數（4 天、20 秒 → 每天約 80 秒查一次）。
- 各天最近一次的結果會合併成完整快照，所以提醒、標題、面板、歷史紀錄都跟原本一樣；
  同一張票不會因為輪到別天而「消失又重複提醒」；某天連續查不到結果超過 5 分鐘，就不再採信它的舊結果。
- 實際間隔 = `max(rotate.everyMs, 預算平均分散)`。被 429 擋到後，預算會自動調降，間隔就自動拉長。
- 這是「更均勻」不是「更安全」：它能不能少被擋，仍要靠實測；請看「限流」一節的紀錄。

### 有票怎麼判斷？

API 每個時段回傳 `sdName`（如 `20회차(18:00 ~ 18:30) 입장`）與 `sdRemainder`（剩餘數）。
`sdRemainder > 0` 就是有票。備援模式下則讀畫面文字 `[剩余:N]`，「售罄」不含數字所以不會匹配。

### 為什麼要攔截 `alert`？

請求失敗時網站會 `alert('요청실패')`。alert 會**阻塞整個分頁**，導致自動化卡死。
腳本在 iframe 載入期間持續把 `alert` 換成「只記錄、不彈窗」的函式（記錄最多保留 50 筆）。

### 如何避免「新票重複通知」？

用 `日期|時段名稱` 當 key，保存上一輪有票的 key 集合，**這一輪有、上一輪沒有**的才算新增。
這份集合也會存進接續存檔：Chrome 中斷不久就重啟，不會重複通知；中斷很久，仍存在的票會重新提醒一次。

### 如何避免多個迴圈／多個分頁同時跑？

- 同一分頁：每次啟動產生唯一 `RUN_ID`，舊迴圈每一步都檢查，發現不是自己就退出。
- 多個分頁：用 `localStorage` 心跳（每 10 秒，Worker 計時）偵測；超過 90 秒沒有心跳就視為對方已不在。
  另一個分頁真的在監控時，新的會拒絕啟動並用中文說明。重新整理或關閉分頁時會主動釋放鎖（`pagehide`），
  所以重新整理後可以立刻重新啟動；只有瀏覽器當機這類意外情況才需要等最多 90 秒。

### 計時器與背景分頁

優先使用 **Web Worker 計時**：Chrome 對背景分頁會把主執行緒的計時器降到每分鐘一次，
Worker 不受同樣限制。若網站的安全設定不允許 Worker，會自動退回一般計時（啟動記錄會註明）。
> 注意：這只保證「程式的排程」不被拖慢；分頁完全被隱藏時，瀏覽器仍可能降低頁面本身的效能，
> 所以仍建議把此分頁放在前景或獨立視窗。

## 中斷後自動接續（Chrome 重啟／分頁重開）

監控程式活在分頁的記憶體裡，**Chrome 重啟、分頁被關掉或重新整理，程式就會消失**。
為了不必每次都從頭摸索，程式會在**每一輪結束後**把以下資訊存進 `localStorage`
（鍵名 `__ticket_watcher_state`）：

- 目前學到的休息間隔、生效的下限、退回用的間隔堆疊
- 已完成輪數、在下限連續成功的次數
- 上次是否以失敗收尾、存檔時間

重新啟動時：

| 情況 | 行為 |
|---|---|
| 沒有存檔，或存檔超過 24 小時 | 從 `interval.start` 重新開始 |
| 有存檔，且中斷時間短（< 10 分鐘）且上次成功 | 直接沿用學到的間隔繼續 |
| 有存檔，但中斷過久（> 10 分鐘）**或**上次以失敗收尾 | 沿用間隔，但**先冷卻 2 分鐘**再開始，避免一啟動就撞上尚未解除的限流 |

想清掉存檔重新開始：`window.__ticketWatcher.resetSaved()`，再重新貼上腳本。

**想讓它在分頁一開就自動啟動？** 請看[自動啟動：Tampermonkey](../README.md#方式-b自動啟動tampermonkeyviolentmonkey-或-adguard)
（專案已附好可直接安裝的使用者腳本）。
> 程式開頭已內建 `if (window.top !== window.self) return;`，只會在最上層視窗執行，
> 不會在腳本自己建立的隱藏 iframe 裡重複啟動（否則會遞迴失控）。

## 使用技術

| 項目 | 說明 |
|---|---|
| 語言／環境 | 原生 JavaScript（ES2020+），單一檔案，**零依賴、無需建置** |
| DOM 操作 | `iframe.contentDocument`、`querySelectorAll`、`click()` |
| 非同步 | `async/await`、`Promise`、`setTimeout`／`setInterval` |
| 資料擷取 | 旁聽頁面自己的 `ajaxComplete` 事件，取 HTTP 狀態碼與 JSON；備援為讀畫面文字 + 正規表示式 |
| 狀態保存 | `localStorage`（歷史紀錄，最多 200 筆）；執行狀態存在記憶體 |
| 提醒 | Web Notifications API、Web Audio（合成提示音）、Web Speech API（語音）、`document.title` 閃爍、動態 favicon、固定定位面板 |
| 計時 | Web Worker 計時（備援：`setTimeout`） |
| 測試 | Node 內建 `node:test`，核心邏輯拆成不碰 DOM 的純函式 |
| 穩定性設計 | 唯一 RUN_ID 防重複、`finally` 清 iframe、攔截 `alert`、自適應退避 |
| 執行方式 | 貼到 Console，或用 Tampermonkey／Violentmonkey／AdGuard（桌面版）作為使用者腳本 |

## 程式**無法**自動處理、需要你自己做的事

1. **打開正確的訂票頁**（程式不能替你決定要監看哪個商品）。
2. **貼上程式並按 Enter**（瀏覽器規定一定要由人操作）。第一次貼可能要先輸入 `allow pasting`。
3. **保持這個分頁在前景、電腦有電有網。** 瀏覽器不允許網頁程式阻止「整台電腦關機／合上螢幕睡眠」。
4. **Chrome 完全關閉重開後，需要重新貼一次**（或改用下一節的 Tampermonkey 自動啟動）。
5. **有票後，你要自己下單付款**，工具不會代勞。
