## 開發者：專案結構與測試

```
haeundae-sky-capsule-ticket-watcher/
├─ watcher.js                 # 主程式（單一檔案，貼到 Console 即可；含 UserScript 標頭）
├─ userscript/
│  └─ haeundae-sky-capsule-ticket-watcher.user.js   # 給 Tampermonkey／Violentmonkey／AdGuard 用的版本（由 watcher.js 自動產生，勿手改）
├─ scripts/
│  ├─ build-userscript.js     # 產生上面那個 .user.js：npm run build:userscript
│  ├─ restart-chrome.command  # 手動重開 Chrome（macOS）
│  └─ restart-chrome.bat      # 手動重開 Chrome（Windows，未實測）
├─ docs/                      # 詳細文件（設定、原理、限流、疑難排解、開發）；README 只放上手需要的部分
├─ test/
│  ├─ core.test.js            # 核心邏輯的單元測試
│  ├─ fake-env.js             # 假瀏覽器環境（假 DOM／jQuery／通知／語音／localStorage…）
│  ├─ integration.test.js     # 用假瀏覽器跑完整流程的情境測試（限流、403、逾時、接續、輪流模式…）
│  ├─ userscript.test.js      # 檢查 .user.js 與 watcher.js 同步、標頭正確、小工具語法與權限
│  └─ docs.test.js            # 檢查 README 與 docs/ 的站內連結和標題錨點都有效、README 不超過 200 行
├─ package.json               # npm test、npm run build:userscript；沒有任何依賴
├─ README.md
└─ LICENSE
```

> **改了 `watcher.js` 之後**，請執行 `npm run build:userscript` 重新產生使用者腳本，並把兩個檔案一起 commit；
> 忘了的話 `npm test` 會失敗（`userscript.test.js` 會比對兩者是否同步）。版本號在 `package.json`，`watcher.js` 標頭的 `@version` 要一致。

- `watcher.js` 分成兩層：**核心邏輯**（`Core`：日期解析、月份計算、HTTP 分類、Retry-After、
  有票判斷、新票比對、自適應間隔控制器…，全是不碰 DOM 的純函式）與**瀏覽器層**（iframe、事件監聽、面板、提醒…）。
- 在 Node 載入時（沒有 `window`）只匯出 `Core`，所以可以直接單元測試：

```bash
npm test          # 或： node --test
```

目前共 127 個測試（`npm test`，約 1 分鐘），分三層：

1. **單元測試**（`core.test.js`，27 個）：日期各種合法／錯誤寫法、月份差計算（含跨年、往前切）、HTTP 狀態分類、
   `Retry-After`（秒數／日期／過期）、有票判斷（字串數字）、新票偵測（持續有票不重複、消失再出現算新增）、
   存檔鍵隔離、間隔控制器、查詢預算與平均分散、設定深層合併。
2. **整合測試**（`integration.test.js`，用 `fake-env.js` 的假瀏覽器把完整的 `watcher.js` 跑一遍）：
   基本流程、有票提醒、備援讀畫面、自動切月份、限流（429）與封鎖期間試探、403 token 過期、逾時、版面改版、
   通知權限與語音、多分頁鎖、接續存檔（含封鎖中重貼程式）、查詢預算、輪流模式、數百輪的壓力測試（檢查記憶體／計時器／儲存都有上限）。
3. **發佈與文件檢查**（`userscript.test.js`、`docs.test.js`）：文件的站內連結與錨點都有效、README 保持精簡；Tampermonkey 用的 `.user.js` 與 `watcher.js` 同步、標頭正確、
   重開 Chrome 小工具語法正確且在 git 裡記錄為可執行、監控程式本體不含「自動重開瀏覽器」之類的呼叫。

> 瀏覽器層（iframe、`ajaxComplete` 旁聽、通知、語音）需要真實頁面，無法在 Node 測。
> 開發時曾因此抓到一個單元測試不可能發現的 bug：`jqXHR` 是類 Promise 物件，直接 `resolve(xhr)` 會被自動拆開，
> 導致拿不到狀態碼。這類問題只能在真實網站上驗證。

## 開發歷程與實測結論

本專案是在實際使用中一步步收斂出來的，以下是踩過的坑（也是設計理由）：

1. **原本每 30 秒掃 22 天** → 短時間累積數百次查詢，觸發 **HTTP 429**，網站回 `요청실패`。
   → 改成只掃需要的日期、加入退避。
2. **嘗試直接呼叫 API** → 回 **403**，因為請求需要頁面產生的 `X-Schedule-Token`。
   → 決定**不繞過**，改回沿用 UI 流程。
3. **舊迴圈「復活」與新迴圈同時跑**，互相覆蓋狀態，造成假性 403。
   → 加入唯一 `RUN_ID` 與 `isAlive()` 檢查。
4. **失敗一次就永遠鎖死在較長間隔**。
   → 加入「在下限連續成功 N 次後放寬」的重新試探機制。
5. **間隔縮到 40 秒後不再縮短**（`40-20 < 30` 的邊界問題）。
   → 改為 `max(floor, interval - step)`，最後一級直接落到下限。
6. **整月 31 天＋休息 5 秒** → 第 3 輪被限流；證實自適應退避有效，並得到「不要太激進」的實測結論。

---

7. **v2：事件驅動重寫。** 一輪從約 23 秒縮到約 4～6 秒；改讀 HTTP 狀態碼與 JSON，精準分類錯誤；
   確認資料屬於被點的那一天；預設不再每輪重載頁面。
8. **持續 50 輪後又被限流**（每輪整頁重載約 9 個請求）。→ 發現每次載入頁面還要跑一次
   `challenge`／`issueToken`（工作量證明，token 有效 10 分鐘），改為沿用同一頁；
   被限流後改為暫停再試 1 個請求，而不是每幾十秒重試。（曾誤把「使用者重開 Chrome 的時間」當成「自己解除的時間」，已更正，見「限流」一節。）
9. **`resolve(jqXHR)` 陷阱**：見上節。
10. **加入查詢預算與診斷**：因為分不出限流的機制，改成「不論哪種機制都有效」的做法——控制總量；
    並讓每次被擋都留下可分析的數字。
11. **預算內仍被擋（17:41）**：預算 90 個/30 分鐘跑了 126 分鐘沒事，之後在窗口內只有 87 個時，於「自動重載頁面後的第一個查詢」被擋。
    → 「90 個以內安全」被推翻；預設預算降到 60、重載改成約 4 小時一次；每次載入頁面與每次被擋都留下更完整的紀錄；
    並補上一個漏洞：封鎖期間重新貼程式，原本只會冷卻 2 分鐘就去試探，現在會等到原本排定的時間。
    原因尚未確定（突發？累積？還是兩者合計？），見「限流」一節。
12. **輪流模式（溫和模式）**：把「每輪連查全部日期」改成「每次只查 1 天、日期輪流查」，消除一次連送 N 個請求的突發；
    平均量不變。各天結果合併成完整快照，提醒邏輯不變。這只是把請求排得更均勻，能否減少被擋仍待實測。
13. **使用者腳本誤報「找不到日曆」（2.1.1）**：用 AdGuard 安裝自動啟動版後，腳本在日曆被網頁畫出來之前就開始檢查，直接報錯。
    確認原始 HTML（約 56 KB）裡沒有 `Next` 也沒有年月標題，日曆是網頁的 JavaScript 事後產生的。→ 啟動時改成先等日曆出現（最多 30 秒），逾時才報錯；貼在 Console 時行為不變。
14. **設定 `everyMs` 卻沒有變快（2.1.2）**：預設預算 60 個/30 分鐘等於每 30 秒 1 個，所以只把 `everyMs` 改成 20 秒，實際仍是 30 秒。
    邏輯本來就是「取較慢者」，但面板沒說明、我的操作說明也漏了 `budget.maxCalls`。→ 面板現在會直接寫「設定是每 N 秒，但受查詢預算限制」，README 補上對照表。
15. **改了設定卻被舊存檔壓回去、預設改為每 20 秒（2.2.0）**：存檔會記住上一次的預算，重啟時 `min(存檔, 設定)`，
    於是把 `maxCalls` 從 60 改成 100 之後，存檔裡上一次留下的 60（其實只是舊的預設值）仍把它壓回去。→ 只有「被擋後學到的」預算才寫入存檔並沿用（`bl` 旗標）。
    同時依實測（每分鐘 6 個約半小時就被擋、每分鐘 3 個曾撐過 2 小時）把預設改成每 20 秒查 1 天、預算 100、約 4 小時才重載一次。
    README 也從 800 多行縮成約 150 行，細節搬到 `docs/`，並加上連結檢查測試。
